## 0.3 跨游戏通用的四条规矩

1. **签名**（三个自编译启动器都适用）
   - 先在 bundle **外面**签名，再拷进去。在 bundle 内签会扫整个 App（16–92 GB，十几分钟且常失败）。
   - 拷进去必须 `ditto --norsrc` + `xattr -c`，`cp -f` 会导致 `SIGKILL (Code Signature Invalid)`。
   - 编译输出**文件名要和 App 内的可执行文件名一致**（ad-hoc 签名的 identifier 由文件名派生）。
2. **Wine 系的路径必须纯英文**。中文路径会被 Wine 转成 `????`，prefix 建不起来。
3. **搬动时保留符号链接**：用 `ditto` / `cp -R` / `rsync -a`，**别用 Finder 拖拽或 `cp -RL`**。
   搬完自检：
   ```sh
   find "/Volumes/SSD/Game/游戏构建" -type l | while read l; do [ -e "$l" ] || echo "断链: $l"; done
   ```
4. **别在外置 USB 盘上直接构建**：慢 3–5 倍，而且中途拔盘即废。先拷到本机再编。

## 2. 情况 A：App 只是被删了 —— 直接拷回来

**不需要编译。** 固态上那份是完整可运行的。

### 2.1 拷回原位

```sh
mkdir -p ~/Games/旷野之息 ~/Games/王国之泪

# 用 cp -cR 做 APFS 克隆：同卷不额外占空间，跨卷就是普通复制
cp -cR "/Volumes/SSD/Game/塞尔达-Mac版/旷野之息/Breath of the Wild.app" ~/Games/旷野之息/
cp -cR "/Volumes/SSD/Game/塞尔达-Mac版/王国之泪/Tears of the Kingdom M3.app" ~/Games/王国之泪/
```

> 16 GB 的 App 跨卷复制在 USB 3.0 上大约 1~2 分钟。**别中途拔盘。**

### 2.2 去掉隔离标记（从网盘下的包才需要）

```sh
xattr -dr com.apple.quarantine ~/Games/旷野之息/"Breath of the Wild.app"
xattr -dr com.apple.quarantine ~/Games/王国之泪/"Tears of the Kingdom M3.app"
```

从本机拷到移动盘再拷回来一般没有隔离标记，可以先跑 `xattr -l <app>` 看一眼，空的就跳过。

### 2.3 也可以直接在固态上跑

实测可行（2026-10-27 验证）：双击固态上那个 `.app` 就能玩，不用拷回本机。

- 存档仍在内部盘 `~/Library/Application Support/MacNativeGames/{BOTW,TOTK}/`，跟着机器走，不跟着 App 走。
- 固态读取实测 301 MB/s，加载比内置盘慢一点，进游戏后差别不大。
- **玩的时候不能拔盘。**
- ⚠️ 从命令行直接 exec 固态上的二进制（`Contents/MacOS/BotW --play`）会静默退出，**只能用双击 / `open -a`**。内置盘那份没这个问题。

### 2.4 存档要不要恢复

App 和存档是分开的。只拷 App 回来，存档还在，直接读得到。

如果连存档也没了，从 `游戏数据/BOTW`、`游戏数据/TOTK` 拷回去：

```sh
mkdir -p ~/Library/Application\ Support/MacNativeGames
cp -R "/Volumes/SSD/Game/塞尔达-Mac版/游戏数据/BOTW" ~/Library/Application\ Support/MacNativeGames/
cp -R "/Volumes/SSD/Game/塞尔达-Mac版/游戏数据/TOTK" ~/Library/Application\ Support/MacNativeGames/
```

## 3. 情况 B：完整重建

### 3.1 环境准备（只做一次）

```sh
# 1) Xcode 命令行工具
xcode-select --install

# 2) Homebrew 依赖：音频（opus）和预渲染影片（libvpx）是硬依赖，缺了链接会失败
brew install opus libvpx python@3.14

# 3) Python 环境（源码树里已经有一个，可以直接用；新机器要重建）
cd "/Volumes/SSD/Game/游戏构建/塞尔达/_构建源码/Build"
python3.14 -m venv venv
./venv/bin/pip install -r work/totk/requirements.txt
```

> 工作树里的 `Build/work/totk/.venv` 是指向 `../venv` 的**相对**符号链接，整个目录搬到哪里都不会断。
> 如果它断了（`ls -la` 显示指向一个不存在的绝对路径），重建一下即可：
> `cd Build/work/totk && ln -sfn ../venv .venv`
>
> 树里还有一个相对链接 `Build/work/totk/tooling/spirv-cross -> ../../src/SPIRV-Cross`，
> 断了就这样修：`cd Build/work/totk/tooling && ln -sfn ../../src/SPIRV-Cross spirv-cross`

**磁盘空间**：一次完整构建需要 **60 GB 以上空闲**。构建过程会解包 romfs、编译图形层、
生成 16 GB 的 App，全在 `--work` 目录里。

> 建议先把 `_构建源码` 从固态拷到本机再构建 —— 在 USB 上编译慢很多，而且中途拔盘就废了。
> 构建完再把产物拷回固态。

### 3.2 王国之泪：XCI 本体 + 1.4.3 更新

```sh
SRC="/Volumes/SSD/Game/塞尔达-Mac版"                  # 游戏素材（xci/nsp/keys）
BUILD="/Volumes/SSD/Game/游戏构建/塞尔达/_构建源码"   # 构建源码
python3 "$BUILD/Source/build_app.py" \
  "$SRC/王国之泪/素材/xci本体/[0100F2C0115B6000][v0].xci" \
  --update "$SRC/王国之泪/素材/upd-v1.4.3/[UPD][v1.4.3][0100F2C0115B6800][v720896].nsz" \
  -k "$SRC/王国之泪/素材/ProdKeys.-v22.5.0/prod.keys" \
  --work "$HOME/SeldaBuild/totk" \
  -o "$HOME/SeldaBuild/out/Tears of the Kingdom M3.app"
```

关键点：

- `--update` 传的是 **`.nsz`**（压缩格式），脚本原生支持，不用先解压。
- **必须产出 Metal 3 目标**。`build_app.py` 靠环境变量 `TOTK_M3=1` 决定给 make 加不加 `-m3` 后缀；
  不加 `-m3` 编出来的是 Metal 4 目标，**在 macOS 15 上跑不起来**。当前版本脚本默认已按 M3 走，
  日志里会出现一行 `Metal 3 build: minimum system macOS 15.0`，**看到这行才算对**。
- 首次构建约 **55 分钟**（M4 / 16 GB，日志实测 00:15 开始、01:10 结束，其中 107 秒花在 macOS
  对新 App 的一次性校验上）。

### 3.3 旷野之息：NSP 本体 + 1.9.0 更新 + 两个 DLC

```sh
SRC="/Volumes/SSD/Game/塞尔达-Mac版"                  # 游戏素材（xci/nsp/keys）
BUILD="/Volumes/SSD/Game/游戏构建/塞尔达/_构建源码"   # 构建源码
python3 "$BUILD/Source/build_app.py" \
```

### 3.5 只改了一点点东西？不用全量重建

| 改了什么 | 跑什么 | 耗时 |
|---|---|---|
| `runtime/*.c` / `*.m` | `cd Build/work/totk && make -j$(sysctl -n hw.ncpu) runtime-v143-m3`（旷野是 `runtime-botw190-m3`），把 `build/totk-native-v143-m3` 拷成 App 里的 `Contents/Resources/totk/build/totk-native`，重签 | 2~4 分钟 |
| `app/launcher.m` | 见下面那条单编命令，拷进 `Contents/MacOS/`，重签 | 5 秒 + 重签 |
| 只改界面文字 | 同上 | 秒级 |

启动器单编（两个游戏靠宏区分，输出文件名不同）：

```sh
cd "/Volumes/SSD/Game/游戏构建/塞尔达/_构建源码/Build/work/totk"

# 王国之泪
xcrun clang -fobjc-arc -O2 -Wall -Ithird_party/d2r_gfx/gfx/nvn -Iruntime \
  -DTOTK_GAME_V143=1 app/launcher.m \
  -framework AppKit -framework GameController -o build/app-launcher-totk

# 旷野之息
xcrun clang -fobjc-arc -O2 -Wall -Ithird_party/d2r_gfx/gfx/nvn -Iruntime \
  -DGAME_BOTW190=1 app/launcher.m \
  -framework AppKit -framework GameController -o build/app-launcher-botw
```

装回去并重签：

```sh
cp build/app-launcher-totk ~/Games/王国之泪/"Tears of the Kingdom M3.app/Contents/MacOS/TOTK"
cp build/app-launcher-botw ~/Games/旷野之息/"Breath of the Wild.app/Contents/MacOS/BotW"

codesign --force --deep --sign - ~/Games/王国之泪/"Tears of the Kingdom M3.app"
codesign --force --deep --sign - ~/Games/旷野之息/"Breath of the Wild.app"
```

> ⚠️ **改任何二进制都必须重签**，否则 App 起不来。
> `--deep` 对 16 GB 的 App 要约 60 秒，前台跑容易被打断 —— 放后台。
> 只换了启动器、`Contents/Helpers` 里那份数据包没动的话，可以不加 `--deep`，只签本体，几秒完成。

## 5. 验收：怎么确认"和原来那个一模一样"


## 7. 已知的坑（会真的卡住你）

| 坑 | 现象 | 处理 |
|---|---|---|
| **中文路径** | 启动器白窗口、几十秒后静默退出 | App 必须放纯英文路径。`~/Games/旷野之息/` 这种目录名没问题，但**别再往里面套中文子目录** |
| **少了 `-m3`** | 编译能过，macOS 15 上启动即崩 | 确认构建日志里有 `Metal 3 build: minimum system macOS 15.0` |
| **改了二进制没重签** | App 双击没反应 | `codesign --force --deep --sign - <app>` |
| **`--deep` 超时** | 命令被中断，签名不完整 | 放后台跑；只换启动器时可不加 `--deep` |
| **构建中断在解包阶段** | 工作树残留半成品，重跑报错 | 删掉 `--work` 目录重来。素材不受影响 |
| **DLC 少传一个** | 游戏里那个 DLC 内容不存在 | 两个 `--dlc` 都要传 |
| **字体缺失** | 构建报 shared fonts 相关错误 | 见 3.3 的字体说明 |
| **在 USB 上直接构建** | 慢 3~5 倍，拔盘即废 | 先拷 `_构建源码` 到本机 |
| **符号链接断了** | `make` 报找不到 SPIRV-Cross / venv | 树里有 2 个相对链接，搬动时**别用 `cp -RL`**（会解引用）。断了就重建，见 3.1 |
| **固态上命令行 `--play`** | 静默退出，无窗口 | 用双击 / `open -a` |

```
/Volumes/SSD/Game/Prototype.rar        8.0 GB  原始素材（不可再生，别删）
```

**关键技术栈**：

```
Windows 版 prototypef.exe（PE32 / i386 / DirectX 9，2009 年的引擎）
  → Wine 11.18 (Staging)，x86_64 Mach-O，整个跑在 Rosetta 2 翻译层下
      └ 游戏是 32 位 PE，走 Wine 的新 WoW64（lib/wine/i386-windows 里的 PE dll + 64 位 unix 侧）
  → wined3d（D3D9 → OpenGL 4.1 core，Apple 的 GL 驱动）
  → Metal → Apple M4 GPU
```

> **为什么不能像塞尔达那样原生跑**：王国之泪是 ARM64 + NVN，机器码能原样执行，补三层 API 就够。
> 虐杀原形是 x86-32 + Win32 + D3D9，**机器码一条都不能直接跑**，只能整条链翻译。
> 这三层（Rosetta 2 / Wine / wined3d）没有一层是能自己写的，能做的是把它们打包成一个自包含 App。

## 第 3 节 · 从零重建（App 整个没了才需要）

### 3.1 准备

- 空闲空间 **≥ 20 GB**（8 GB 素材 + 8.6 GB App + prefix）
- 路径必须**纯英文**。中文路径会被 Wine 转成 `????`，引擎初始化直接失败（白窗口后静默退出）
- 时间：解压 8 GB 约 5–8 分钟，构建 + 签名约 2 分钟，首次启动建 prefix 约 1 分钟

### 3.2 解素材

`Prototype.rar` 里是两个目录：`Prototype/`（游戏本体）和 `_CommonRedist/`（运行库，Wine 下不需要）。

```sh
mkdir -p ~/Games/Prototype/_src
cd /tmp && bsdtar -xf "/Volumes/SSD/Game/Prototype.rar" Prototype
mv Prototype ~/Games/Prototype/_src/Game
```

Wine 运行时不在 rar 里，要单独取：**Gcenx 的 wine-staging 11.18 osx64 包**，解开后目录里应该有 `bin/ lib/ share/`：

```sh
mv wine-staging-11.18-osx64 ~/Games/Prototype/_src/Wine
~/Games/Prototype/_src/Wine/bin/wine --version    # 要打印 wine-11.18 (Staging)
```

### 3.3 构建

```sh
cd "/Volumes/SSD/Game/游戏构建/虐杀原形/_build"
python3 build_prototype.py            # 完整构建：Wine + Game + 启动器 + 签名
```

`build_prototype.py` 会用 `cp -cR`（APFS 克隆，同卷不额外占空间）把两份素材拷进 App，
再编译启动器、写 `Info.plist`、`codesign --force --sign -`（ad-hoc，不加 `--deep`）。

### 3.4 只改启动器的话（99% 的情况）

```sh
cd "/Volumes/SSD/Game/游戏构建/虐杀原形/_build"
python3 build_prototype.py --launcher      # 编译 + strip + 重签，几秒
codesign -v "$HOME/Games/Prototype/Prototype.app" && echo 签名 OK
```

App 不在默认位置时：`PROTOTYPE_ROOT=/别的/路径 python3 build_prototype.py --launcher`。

### 3.5 首次运行

```sh
touch "$HOME/Library/Application Support/MacNativeGames/PROTOTYPE/autoplay"   # 可选：跳过面板
open -a "$HOME/Games/Prototype/Prototype.app"
```

会依次发生：

1. 弹「想要访问"文稿"文件夹」→ **点允许**（存档在 `~/Documents/Prototype`，一次性）
2. 出现面板（第一次会写 `launcher-settings.json`）
3. 点「开始游戏」→ 首次会先 `wineboot -u` 建 prefix（约 1 分钟，没有进度条，别以为卡死）
4. 黑窗口 → 十几秒后出 `RADICAL ENTERTAINMENT` 片头（这一步实测能跑到 400 多帧）
5. 主菜单 → 载入存档

> 如果第 4 步卡在黑窗口不动：先看 `logs/launcher.log` 最后几行——
> 如果是「判定启动失败 + 重试」，说明命中了启动崩溃，看门狗会自己重来（打了 wow64cpu 补丁后
> 这一类实测 12 次 0 次）；如果日志里有「wow64cpu 补丁：未打」，先把它打上（第 10 节）。
> 如果既没重试也没出片头，多半是第 6 节第 19 条那个「从 Finder 启动」的问题，改用终端启动。

## 第 4 节 · 启动器面板

源码 `_build/launcher.m`（AppKit，无 nib）。**面板选项 → 落到哪里**：

| 面板项 | 落到 | 说明 |
|---|---|---|
| 渲染后端 | `WINEDLLOVERRIDES` | wined3d：`d3d9=b;winevulkan=d`；DXVK：`d3d9=n`。`Game/d3d9.dll` 不存在时这一项**直接灰掉**并强制 wined3d |
| 显示模式 | **Wine 注册表虚拟桌面**（窗口）或删掉该值（独占全屏） | 两种模式**启动命令完全一样**（`wine prototypef.exe`），只是注册表不同。窗口模式下启动器会用辅助功能 API 把窗口摆到屏幕正中 |
| 分辨率 | 只决定**虚拟桌面尺寸**（`HKCU\Software\Wine\Explorer\Desktops\Prototype`） | 不改变游戏内部渲染分辨率；**建议和游戏内 OPTIONS → VIDEO 的分辨率一致**，否则窗口里会出现黑边 |

| 帧率上限 | 写 `dxvk.conf` 的 `d3d9.maxFrameRate` | **wined3d 忽略它**；真正的锁帧靠游戏内 VSync |
| 日志 | `WINEDEBUG`（正常 `err+all`，详细 `,fixme+all`） | 不能用 `-all` |
| 提高进程优先级 | `taskpolicy -c user-interactive -p <wine pid>` | 减少被后台任务抢占的掉帧 |
| 把帧率写进日志 | `WINEDEBUG` 追加 `,fps` | 排查用，会明显掉帧，平时别开 |
| 备份存档 | 拷 `~/Documents/Prototype/*.bin` → `saves-backup/<时间戳>/` | 存 16 KB 一个，几乎不花钱 |

## 第 6 节 · 坑位清单（按严重程度排序，都踩过）

1. **App 路径不能有中文**。游戏用 ANSI 接口取自己的目录，中文会变 `????`，引擎初始化失败：
   白窗口 → 几十秒 → 静默退出。所以 App 叫 `Prototype.app` 而不是 `虐杀原形.app`。
2. **DXVK 这条路走不通，而且失败方式是"点了没反应"**。`d3d9=n` 的前提是 `Game/` 里有原生 `d3d9.dll`；
   没有的话 wine 找不到库，进程起不到一秒就退，**日志一个字都不留**。现在按文件存在与否自动灰掉这一项，
   启动前再拦一次，设置里存着 DXVK 也会自动切回 wined3d。
3. **配置文件不能写进 App 包里**。以前 `dxvk.conf` 写在 `Game/` 下，等于每次点开始游戏都在改 bundle 里的文件——
   codesign 的资源封印记的是内容哈希，内容一变 ad-hoc 签名就作废（`codesign -v` 报 resource modified）。
   现在写 `…/PROTOTYPE/dxvk.conf`，用 `DXVK_CONFIG_FILE` 指过去。
4. **`WINE_CPU_TOPOLOGY` 不能省**。不限制核心时 Wine 里会 `RtlpWaitForCriticalSection` 死锁，
   然后 `Exception frame is not in stack limits` 崩溃，一般跑一两分钟就挂。4 核是游戏自带 `Restrict Cores.bat`
   的值（`start /affinity F`）。
5. **`WINEDEBUG=-all` 是陷阱**。崩溃信息会被吞掉，看门狗没法判断，表现就是"卡在黑窗口里永远不动"。
   `err+all` 是安全下限。（早先还观察到 `-all` 会显著提高崩溃概率——现在看那只是同一个 Rosetta
   问题的巧合，不再作为结论。）
6. **强杀会留下占着 prefix 的服务进程**。`services.exe` / `winedevice.exe` / `plugplay.exe` 的命令行里只有
   `C:\windows\system32\...`，没有 App 路径，所以 `pkill -f "Resources/Wine"` 抓不到它们。
   正确做法是按**可执行文件路径**枚举（启动器里的 `CollectWinePids` 就是这么干的，用的是 `proc_pidpath`）。
7. **`open --args` 不保证把参数送进进程**。macOS 15 上实测：面板出来了，但 `arguments` 里没有 `--play`，
   于是永远不开始。所以加了 `autoplay` 标记文件这条路，任何启动方式都成立。
8. **启动崩溃的真正根因：Rosetta 2 的 32/64 位模式切换（已根治）**。
   崩溃长这样，而且**跟游戏本体、显卡、分辨率、模组全都无关**：
   ```
   wine: Unhandled page fault on read access to 00002DC1 at address 7BF21239 (thread 010c), starting debugger...
   err:virtual:virtual_setup_exception nested exception on signal stack addr 0x7ff80d259ef4 stack 0x7ff001caf980
   err:seh:NtRaiseException Exception frame is not in stack limits => unable to dispatch exception
   ```
   用 `WINEDEBUG=+module` 抓模块表可以看出来：`0x7BF20000` 是 `wow64cpu.dll` 的装载基址，
   偏移 `0x1239` 和 `0x1135` 正好是 syscall / unixcall 的 **32→64 位入口 thunk**。反汇编这两处：
   ```
   +0x1239:  8b 15 c1 2d 00 00   mov edx,[rip+0x2dc1]     ← 读 0x2DC1
   +0x1135:  8b 15 c5 2e 00 00   mov edx,[rip+0x2ec5]     ← 读 0x2EC5
   ```
   虐杀原形是 PE32，在 Apple Silicon 上只能走 Wine 的新式 WoW64（64 位进程里装 32 位 PE），
   每次系统调用都要在两种 CPU 模式间切换。Rosetta 2 偶尔**不真正切换**，于是 CPU 还在 32 位模式下
   执行 64 位的跳转指令，把指令里的位移字段当成内存地址去读 —— 那个低地址当然不存在，必然 page fault。
   这一条解释了全部怪现象：为什么是**概率性**的、为什么重试有时能成、为什么 64 位的霍格沃茨完全没事。

   **修法**：给 `wow64cpu.dll` 打二进制补丁（`_build/wow64cpu_rosetta_patch.py`，
   逻辑取自 GitHub 上 [altium-wine](https://github.com/lazy-jubei/altium-wine) 的同名补丁）——
   两个 32→64 入口改走"能判断当前 CPU 模式"的 trampoline（`push 0x2b; push ecx; retf` 重试切换），
   两个 64→32 返回站点改成在栈上构造 `iretq` 帧后用 `iretq` 返回。补丁先校验四个站点的原始字节，
   对不上就拒绝执行；原文件备份为同目录 `wow64cpu.dll.orig`。改完必须重新签名：
   ```
   codesign --force --deep -s - ~/Games/Prototype/Prototype.app
   ```
   实测 **12 次启动 0 次崩溃**（打补丁前 11 次样本 6 次成功）。
   Note：Wine 官方把这类问题判成 NOTOURBUG（Rosetta 侧的问题），所以换 Wine 版本补丁会消失、
   也不会被官方修掉——`launcher.log` 里每次启动都写一行 `wow64cpu 补丁：已打 / 未打`，就是判据。

9. **看门狗仍然要留**。补丁之后还剩下两种少见失败，都靠它兜：
   ```
   日志停在同一行，没有任何崩溃特征，卡在 800×450 黑窗口里（静默卡死）
   ```
   这种情况用 CPU 判据——**20 秒内整个会话吃掉不到 0.2 CPU 秒 = 没在干活**。
   阈值是标定出来的，不是拍的（`proc_pid_rusage` 实测，`launcher.log` 里每次都会写一行 `CPU 判据`）：

   | 状态 | 20 秒窗口累计 CPU |
   |---|---|
   | 健康启动（正在解包/编译着色器/出帧） | **0.50 ~ 0.74 秒** |
   | 静默卡死（主线程等一个不来的事件） | **0.03 ~ 0.11 秒** |

   不要用"多少秒没画面"——游戏跑起来之后日志本来就不再输出，这条规则会把正在玩的一局误杀。
10. **看门狗和进程退出回调会重复记账**。崩溃退出时两条路径都会走到"重试"，各 `attempt++` 一次，
    5 次预算变成了 2 次半（实测：第 3 次失败后日志直接跳到「第 5 次」）。用 `watchdogFired` 标记
    让退出回调在看门狗已经判死的情况下直接返回。
11. **`wineserver -k` 不能等它的回调**。崩溃现场常挂着 `winedbg`，`-k` 有时卡住不返回，回调不触发就永远不重试。
    必须自己轮询"进程真的没了"再重启，而且**不能立刻重启**（`-k` 是异步的，1.5 秒后重开会撞上没退干净的旧会话）。
12. **看门狗日志定位要用分隔行，不能用文件偏移**。日志里每次启动写一行
    `===== 第 N 次启动 <时间> =====`，按偏移量算一旦错位就会去扫上一次的崩溃信息然后误判。
13. **wined3d 把显卡厂商认成 NVIDIA**。日志里 `Received unrecognized GL_VENDOR "Apple". Returning HW_VENDOR_NVIDIA.`
    是 fixme 级噪音，不影响运行；注册表里改 `DriverDesc` 也没用，它看的是 GL 返回的厂商串。
14. **`GL_ARB_uniform_buffer_object` 之类的 GLSL 扩展警告是噪音**。日志里几百条，
    是 Apple 的 GLSL 编译器在 core profile 下的输出，不影响画面也不影响帧率。
15. **虚拟桌面尺寸 ≠ 游戏内渲染分辨率**。面板的分辨率只决定那个窗口多大，游戏自己画多少在 OPTIONS 里改。
16. **锁帧只有一条路**：游戏内 `OPTIONS → VIDEO → Vertical Sync = ON`（写进 `profile.bin`，设一次就够）。
    wined3d 忽略 `dxvk.conf` 的 `maxFrameRate`。VSync 关掉时片头能跑到 490 fps，对无风扇的 Air 是白烧电。
17. **补丁后仍有一种独立失败**：`err:d3d:wined3d_swapchain_resize_buffers Something's still holding back buffer 0`
    （交换链 resize 时挂掉，12 次里出现 1 次）。跟 wow64 那条无关，看门狗重试一次就过去了；
    如果它变频繁，先把面板改成「窗口模式」而不是虚拟桌面。
18. **别同时开两个启动器**。没有单实例保护，两个会话会抢同一个 prefix，两个都别想正常跑。
19. **`open -a`（等于双击）和目录里直接跑 App 二进制，行为不一定一样**。实测到的确定差别只有一条：
    用 `open -a` 时，虚拟桌面模式下的 explorer 会起来、但**游戏进程永远不出现**
    （日志只有 171 行 explorer 初始化，21 秒烧 0.03 CPU 秒）；同一个命令从 shell 起就正常拉起游戏。
    已排除：`LANG` 缺失、`TMPDIR`、`stdin`、自动启动延迟、`taskpolicy` 高优先级，
    以及用 `env -i` 复刻 LaunchServices 的最小环境（复刻不出来）——所以不是环境变量，是会话上下文。
    兜底已加：虚拟桌面 8 秒内见不到游戏进程就自动改直连（写进 `launcher.log`），并把选择记进设置
    `forcedirect`；「重置环境」会清掉它。
    **注意**：黑屏 0 fps 那种现象后来又出现在所有路径上（包括本来正常的 shell 路径），
    所以它和上面这条不是同一个问题，见第 20 条。
20. **黑屏 0 fps**：窗口出来了、一直是黑的、日志里 `@ approx 0.00fps` 并且行数不再增长。
    游戏进程活着、CPU 也不是 0，所以**看门狗的 CPU 判据抓不到**，会一直挂着。
    实测是在反复切换「虚拟桌面 / 独占全屏」之后出现的，怀疑游戏把显示模式写进了
    `~/Documents/Prototype/profile.bin`，之后每个会话都按那个模式建不出可用的交换链。
    恢复顺序（从轻到重）：
    1. 能进画面的话，游戏内 `OPTIONS → VIDEO` 把分辨率/全屏改回 1280×720 + 窗口
    2. 进不去就**备份后**删 `profile.bin`（它是画面设置 + 进度索引；存档在 `slot-*.bin`，不受影响）：
       ```sh
       mkdir -p ~/Documents/Prototype.bak
       cp ~/Documents/Prototype/profile.bin ~/Documents/Prototype.bak/
       rm  ~/Documents/Prototype/profile.bin
       ```
    3. 还不行就重启一次 Mac（清 WindowServer/GPU 状态），或点面板「重置环境」
    判据：正常启动第一帧就是几百 fps（`@ approx 490.34fps`），`0.00fps` 就是坏状态。
21. **启动崩溃的最后一块：MoltenVK（2026-10-30 定位并根治）**。
    症状：启动 3 秒左右直接退出，`launcher.log` 写「启动后 3.2 秒就退出（代码 5）」或
    「启动静默卡死」，`prototype.log` 里唯一的相关行是
    ```
    00f8:err:seh:send_debug_event Exception c0000005 in system thread at 0x7ff81136a622
    ```
    它不是 wow64cpu 那条（地址不在 `0x7BF2xxxx`），所以打完 wow64 补丁仍然会发生。
    真凶是 **wined3d 初始化时会无条件建一个 Vulkan 实例做能力探测**——日志里那一大段
    `[mvk-info] MoltenVK version 1.4.0 ... Created VkInstance` 就是它。这个初始化在 Rosetta 下
    会概率性把进程带崩。`WINEDLLOVERRIDES` 里的 `winevulkan=d` **管不住它**（探测走 unix 侧
    直接 dlopen），所以之前一直以为「已经关了 Vulkan」其实没关。

    **修法**：把 `Contents/Resources/Wine/lib/libMoltenVK.dylib` 改名成 `.disabled`
    （构建脚本 `step_tweaks()` 会自动做，改完必须重新签名）。D3D9 走 OpenGL，用不到 Vulkan，无副作用。
    实测：开着 4 次启动挂 1~2 次；禁掉之后**连续 4 次全成功**（片头 386~498 fps），
    走启动器（双击）路径又连测 3 次，全部第 1 次就起来。
    `launcher.log` 每次启动都会写一行 `MoltenVK：已禁用 / 未禁用`，就是判据。
22. **窗口化不要再用 `wine explorer /desktop=...`**。从 LaunchServices（双击 / `open -a`）启动时，
    explorer 能起来但游戏进程永远不出现——日志只剩一百多行 explorer 初始化，20 秒烧 0.03 CPU 秒。
    同一份命令从终端跑就正常，复刻环境变量也复刻不出来（是会话上下文差异）。
    现在改成**写 Wine 注册表**：
    ```
    HKCU\Software\Wine\Explorer            Desktop = Prototype
    HKCU\Software\Wine\Explorer\Desktops   Prototype = 1024x768
    ```
    启动命令退化成最可靠的 `wine prototypef.exe`，由 wine 自己建虚拟桌面窗口。
    全屏模式 = 删掉 `Desktop` 这个值。实测双击路径也正常。
23. **窗口居中要用辅助功能 API，而且只对虚拟桌面窗口安全**。
    Wine 的虚拟桌面窗口默认贴在屏幕左上角（`0,25`），要用 `AXUIElementSetAttributeValue(kAXPositionAttribute)`
    摆到正中（`1024x768` 在 1920×1080 上就是 `448,156`）。启动器 `startCentering` 干这件事。
    - 需要给**启动器**授权「辅助功能」。签名要求已经固定成 `identifier`
      （`build_prototype.py` 里的 `--requirements`），所以重建启动器**不会**让授权失效。
    - 授权之后必须退出启动器（Cmd+Q）重开一次——运行中的实例会缓存旧的 TCC 判定。
    - **不要对「直连」窗口做同样的事**：直连模式下那个窗口是游戏自己的交换链窗口，
      用 AX 挪它会让画面错位，接着游戏直接退出（代码 0）。

## 第 9 节 · 性能基线与调优边界

**实测数据（1280×720 虚拟桌面，4 核，VSync 关，2026-10-28）**：

| 阶段 | FPS | 备注 |
|---|---|---|
| 片头 logo / 加载 | **330 ~ 490** | `wglSwapBuffers` 节拍实测，这一阶段的帧率上限就是驱动能吃下的量 |
| 主菜单（城市背景） | **8 ~ 19** | 上一版实测；同一套环境、同一个进程 |
| 单次启动成功率 | **12/12（补丁后）**；补丁前约 50%（11 次样本 6 次成功） | 判据是 45 秒窗口内是否出现 `page fault`，见 `_build/soak3.sh` |

启动崩溃的分布（补丁前 `launcher.log` 累计）：page fault（`wow64cpu` 模式切换，见第 6 节第 8 条）
和静默卡死大约各占一半。**打完 wow64cpu 补丁后 page fault 这一类不再出现**，
12 次里只剩 1 次交换链 resize 失败（第 6 节第 17 条）。

**瓶颈判断（决定哪些优化有用）**：

- 同一套配置，片头 490 fps、主菜单 10 帧 → **不是分辨率、不是填充率、不是显存**。
  差别在这一幕的绘制量：wined3d 要把每条 D3D9 调用翻译成 OpenGL，而 Apple 的 OpenGL 驱动早就停止维护；
  再叠上 Rosetta 2 翻译 32 位 x86 指令。**瓶颈在 CPU 侧的翻译链。**
- 所以「降分辨率 / 降画质」对主菜单收益有限——它减的是 GPU 的活，而 GPU 不是瓶颈。
- 真正能减的只有"少画东西"：关阴影、降细节（减少 draw call 数量），这在游戏内 OPTIONS 里。
  这一项没在本机做过逐档对比，别把它当成定论。

**还能做的**：

1. 关掉其它吃内存/CPU 的 App（这台是 16 GB，效果最直接）。
2. 主菜单卡就卡着——它只是菜单。进游戏场景之后再看帧率，才是真实体验。
3. 游戏内 `OPTIONS → VIDEO`：降分辨率、关阴影、关 AA。能跑满的场景把 VSync 打开省电。

**别做（都试过，白费时间）**：

| 想法 | 结论 |
|---|---|
| 换 DXVK | Metal 没有几何着色器（`VkPhysicalDeviceFeatures` 第 5 个字段），MoltenVK 报不出来，D3D9 的 DXVK 实现必然建不出设备。换 MoltenVK 版本没用 |
| wined3d 的 Vulkan 渲染器 | 能起来，一画就崩 `0xc0000005 in vkCreateBufferView` |
| 用 D3DMetal（霍格沃茨那套 GPTK 3.0-3） | GPTK 的 `wine/i386-windows/` 里**只有 `ddraw.dll`，没有 `d3d9.dll`**——D3DMetal 不做 D3D9。这条路对本游戏不存在 |
| vkd3d-proton | 需要 `VK_EXT_transform_feedback`（Metal 没有 stream output），而且它是 D3D12 的，跟 D3D9 无关 |
| 关日志（`-all`）提速 | 会显著提高启动崩溃概率，还吞掉看门狗的依据。得不偿失 |
| 加 `vulkan-1=d` 降崩溃 | 实测 2/6，比不加更差，已排除 |

## 第 2 节 · 从零全量构建

### 2.1 准备

- 空闲空间 **≥ 20 GB**（8 GB 素材 + 8.6 GB App + prefix）

- **别在外置 USB 盘上构建**：慢 3–5 倍，中途拔盘即废。先拷到本机再编

### 2.2 解素材

```sh

~/Games/Prototype/_src/Wine/bin/wine --version     # 必须打印 wine-11.18 (Staging)
```

### 2.3 跑构建

```sh
cd "/Volumes/SSD/Game/游戏构建/虐杀原形/_build"
```


它只跑第 3、4 步（编译 + 运行时改动 + 签名），不碰 Wine 和游戏数据。
`--launcher` 也会走 `step_tweaks()`（幂等，已禁用就跳过）和 `step_app()`（重新签名）。

> **重编前先退出启动器**（Cmd+Q）。运行中的实例占着 `Contents/MacOS/Prototype`，
> 覆盖会失败或留下半个二进制。

## 第 4 节 · 构建期必须做的三个改动

这三条不是"优化"，是不做就会出问题。

### 4.1 禁用 MoltenVK（`step_tweaks()`）

`wined3d` 初始化时会**无条件建一个 Vulkan 实例**做能力探测——日志里那大段
`[mvk-info] MoltenVK version 1.4.0 ... Created VkInstance` 就是它。
这个初始化在 Rosetta 下会概率性把进程带崩，唯一痕迹：

```
00f8:err:seh:send_debug_event Exception c0000005 in system thread at 0x7ff81136a622
```

地址**不在** `0xBF2xxxx` 区间，所以 wow64cpu 补丁治不了它。
而 `WINEDLLOVERRIDES` 里的 `winevulkan=d` **也挡不住**——那段探测是 unix 侧直接
`dlopen libMoltenVK.dylib`，绕过了 DLL 覆盖。

**做法**：把 `Contents/Resources/Wine/lib/libMoltenVK.dylib` 改名成 `.disabled`。
D3D9 走 OpenGL，用不到 Vulkan，无副作用。

**效果**：开启时 4 次启动挂 1~2 次；禁用后 **4/4 全成功**（片头 386~498 fps），
双击启动器路径再测 3/3 全部第 1 次就起来。

### 4.2 签名要求固定成 `identifier`（`step_app()`）

```sh
codesign --force --sign - \
  --requirements '=designated => identifier "org.macnativegames.prototype"' "$APP"
```

**为什么**：ad-hoc 签名默认的 designated requirement 是 `cdhash H"…"`，
而 cdhash 每次重建都会变 → 所有 TCC 授权（辅助功能、文稿目录）全部失效，
用户每次重建都得重新点一遍开关。固定成 identifier 之后重建不再影响已有授权。

这是从鬼泣4 那边搬过来的结论（那边为这个坑反复返工过）。**构建脚本里已经写死，别删。**

### 4.3 清 `cstemp` + 清 xattr（`step_app()` 里）

```sh
find "$APP" -name "*.cstemp" -delete
xattr -cr "$APP"
```

上一次签名被打断会留下 `Contents/MacOS/Prototype.cstemp`，它会被写进资源封印，
之后 `codesign -v` 永远报 `a sealed resource is missing or invalid`（踩过，排查很久）。
清 xattr 是为了避免 `com.apple.provenance` 之类带进新签名。

## 第 7 节 · 构建相关坑位（按严重程度）

1. **忘了禁 MoltenVK** → 启动 3 秒左右直接退出，日志只有
   `Exception c0000005 in system thread`。`launcher.log` 会写 `MoltenVK：未禁用`，一眼可查。
2. **签名没带 `--requirements`** → `codesign -d -r-` 显示 `cdhash H"…"`。
   后果：重建后辅助功能授权失效 → 窗口不再居中（停在左上角）；文稿目录授权也会重新弹。
3. **`cstemp` 残留** → `codesign -v` 报 `a sealed resource is missing or invalid`，
   而且重签也修不好（因为 `.cstemp` 会被重新封印进资源清单）。必须先 `find -delete` 再签。
4. **编译输出文件名不是 `Prototype`** → ad-hoc 签名的 identifier 由文件名派生，
   与 `Info.plist` 的 `CFBundleExecutable` 不一致时会被判签名无效（`SIGKILL`）。
5. **在 bundle 内直接签名 8.6 GB 的包并加 `--deep`** → 扫全树，几十秒到几分钟。
   现在脚本**不加 `--deep`**，只签本体；Wine 树放 `Resources` 当普通数据。
6. **构建时启动器还在跑** → 覆盖 `Contents/MacOS/Prototype` 失败或留下半截文件。
   先 `pkill -9 -f 'MacOS/Prototype'`。
7. **素材路径带中文** → Wine 把路径转成 `????`，prefix 建不起来，白窗口后静默退出。
8. **换了 Wine 版本忘了重打 wow64cpu 补丁** → 启动崩在 `page fault … at address 7BF21239`
   （或 `7BF21135`）。`launcher.log` 会写 `wow64cpu 补丁：未打`。
9. **改 `launcher.m` 后忘了重编就以为改生效了** → 面板看起来变了但行为没变。
   认准 `python3 build_prototype.py --launcher` 跑过、且 `codesign -v` 通过。
10. **顺手把 `--requirements` 那段删掉"简化一下"** → 回到坑 2。这行是刻意的。

### 3.2 装出原始 app

### 3.3 换成 GPTK 3.0-3 渲染层

原厂自带的是 GPTK 17 版，必须换 3.0-3，否则 D3D12 初始化不过。

三个组件，**换之前先改名备份成 `*.orig17`**（本机已经这么做了，所以现在直接跳过这步）：

```sh
# 1) D3DMetal.framework
# 2) external/libd3dshared.dylib
# 3) wine/x86_64-windows（整个目录）
```

GPTK 3.0-3 从 Gcenx 的 `apple-gptk` 分发里取，校验 `D3DMetal` 二进制 sha256 应与分发一致。

### 3.4 修 bundle 里三个必坏的配置

```sh
APP="/Volumes/SSD/Game/HogwartsLegacy/Hogwarts Legacy.app"
SUP="$APP/Contents/SharedSupport"

# ① libinotify 缺失 → wineserver 起不来
ln -sf ../../../Frameworks/libinotify.0.dylib "$SUP/wine/lib/libinotify.0.dylib"

      "$SUP/prefix/dosdevices/e:" "$SUP/prefix/dosdevices/e::"

```

### 3.5 编译并安装启动器（这一步决定能不能双击玩）

```sh
bash "/Volumes/SSD/Game/游戏构建/霍格沃茨之遗/_build/build_launcher.sh"
```

脚本会同时装 `hl_mouse`（鼠标锁定辅助进程）并 ad-hoc 签名。手工装的话：

```sh
clang -fobjc-arc -O2 -framework AppKit -framework Carbon -o /tmp/hl_mouse _build/hl_mouse.m
codesign --force --sign - /tmp/hl_mouse
ditto --norsrc /tmp/hl_mouse "$APP/Contents/MacOS/hl_mouse"; chmod 755 "$APP/Contents/MacOS/hl_mouse"
xattr -c "$APP/Contents/MacOS/hl_mouse"
```

`hl_mouse` 的行为：
- **默认锁定**：窗口一出现就把光标锁在窗口内（`CGWarpMouseCursorPosition` + `CGAssociateMouseAndMouseCursorPosition(false)` + `CGDisplayHideCursor`）；
- **按 0 切换**：脱离 → 普通系统光标、可去桌面；再按 0 锁回。热键是**全局注册**的（和塞尔达一样），
  游戏运行期间 `7` 会被系统吃掉；不要就在面板里取消勾选。
- 热键注册失败时**不自动锁定**（否则没有解锁手段），日志会写明；
- 游戏进程退出 / SIGTERM / SIGHUP 都会先解锁再退，**绝不会把鼠标锁死**；
- `kill -USR1 <pid>` 等价按一次 0，方便脚本调试。
- **不要**改成"按前台 App 自动解锁"：实测 `NSWorkspace.frontmostApplication` 在 Wine 窗口上会抖，
  锁/解锁每秒来回切（踩过）。

脚本里已经封好了三条硬规矩，**别手工改成 `cp`**：

1. **编译输出必须直接叫 `/tmp/Sikarugir`**。ad-hoc 签名的 identifier 由文件名派生，叫 `hl_launcher` 会得到 `hl_launcher-<uuid>`，与 bundle 里的文件名不一致 → 系统判签名无效。
2. **先签名、再拷进 bundle**。在 bundle 内签会触发 `ResourceBuilder::scan` 扫 92 GB（16 分钟且失败，因为 `Contents/Cheat Engine.app` 未签名）。
3. **拷进去必须 `ditto --norsrc` + `xattr -c`**。实测用 `cp -f` 覆盖同一个路径后，系统会判 `SIGKILL (Code Signature Invalid)` / `Taskgated Invalid Signature`，表现是双击完全没反应，只在 `~/Library/Logs/DiagnosticReports/` 里留一份 `bug_type 309` 报告。换 `ditto` 就正常（顺带清一下扩展属性更保险）。

## 第 6 节 · 坑位清单（重建时最容易踩的，按严重程度排序）

1. **中文路径** → Wine 转成 `????`，`wine.inf` 更新失败，prefix 建不起来。目录必须纯英文。
2. **`DYLD_FALLBACK_LIBRARY_PATH` 少了 `Contents/Frameworks`** → 找不到 `libfreetype.6.dylib` → **所有窗口客户区塌成 0** → 启动时的对话框变成 6×54 的空壳（"小横条"）→ 点不动 → 游戏永远卡在等它。日志里会有十几条 `Wine cannot find the FreeType font library`。这是本机折腾最久的一个坑。
3. **`WINE_CPU_TOPOLOGY` 不能省** → 崩溃。
4. **三个 `D3DM_*` 开关不能加** → 崩溃。
5. **强杀游戏会留下 Wine 服务进程** → `services.exe` / `winedevice.exe` / `plugplay.exe` / `svchost.exe` 的**命令行里没有路径**（只有 `C:\windows\system32\services.exe`），`pkill -f "SharedSupport/wine"` 抓不到。它们占着 prefix，下次启动就卡在 `wineboot --init`（wine 进程只有 5 MB / 4 线程、不加载任何图形库）。清理用 `pkill -9 -f 'windows.system32'`。
6. **shell 脚本不能当 app 的主可执行文件** → LaunchServices 会把 app 记成"常驻运行"，之后 `open -a` / 双击只会去"激活"它，报 `Application ... was already running and so the additional environment variables could not be set`。必须用真 Mach-O。
7. **主程序必须用 `ditto` 安装，别用 `cp`**（见 3.5）。`cp -f` 覆盖后会被判签名无效、双击无反应。
8. **编译输出必须叫 `/tmp/Sikarugir`**（见 3.5）。
9. **TCC 授权**：外置盘上的 app 首次双击要授权「可移除宗卷」。从终端跑则走终端的 FDA 权限、不弹窗 —— 所以"终端能跑、双击不行"是正常现象，不是坏了。
10. **注册表改 `DriverVersion` 没用**。注册表里 `DriverDesc` 早就被游戏自己改成 `Apple M4` 了，照样弹警告 —— 它看的是 D3DMetal 报的厂商/版本。只有 `D3DM_VENDOR_ID` 有效。
11. **`AGX: exceeded compiled variants footprint limit`** 是良性警告，正常跑通时也会出现，不用管。
12. **vkd3d-proton 这条路走不通**（别再试）：MoltenVK 能跨过 Vulkan 1.3 门槛，但 vkd3d-proton 2.13/3.0.1 都硬性要求 `VK_EXT_transform_feedback`，**Metal 没有 stream output，MoltenVK 不提供**，报 `Lacking support for transform feedback` 后销毁设备退出。
13. **启动器开锁文件必须带 `O_CLOEXEC`**。不加的话 `auto_dismiss.py` / `caffeinate` / `hl_mouse` 会继承这个 fd，
    启动器退出后锁还被它们占着 → 下次双击被误判成"游戏已经在运行了"直接退出（表现为点了完全没反应）。
    正确写法：`open(lockp, O_WRONLY | O_CREAT | O_CLOEXEC, 0644)`。
14. **辅助进程要能自己收工**。`auto_dismiss.py` 原来只等窗口名含 `Hogwarts Legacy`，
    但有时窗口名是 `HogwartsLegacy`（没空格），于是它会一直挂着。已加 `os.kill(pid, 0)` 检测：
    游戏进程没了就退出。
15. **启动器启动游戏后要释放 UI**：`self.window.contentView = nil; self.window = nil;` + 把控件置 nil +
    切 `NSApplicationActivationPolicyProhibited`，进程从 21 MB 降到 ~10 MB，只留一个 `waitpid`。

## 第 9 节 · 性能基线与调优边界

**实测数据（1280×720，画质最低，2026-10-28）**：

| 场景 | FPS | GPU 耗时 | CPU 侧 Pre | 内存 |
|---|---|---|---|---|
| 主菜单 | 60（被 `t.MaxFPS` 钉住） | 12.7 ms | 22.5 ms | 9.0 GB |
| 载入中 | 35 | 11.1 ms | 22.7 ms | 10.6 GB |
| 室内（宿舍） | 56 | 12.6 ms | 24.1 ms | 13.8 GB |

**瓶颈判断（重要，决定了哪些优化有用）**：

- GPU 只吃掉 12 / 16.7 ms，**CPU 侧 Pre 更长** → 瓶颈是 Rosetta 2 指令翻译 + D3DMetal 命令翻译。**降画质、降分辨率基本无效。**
- 游戏进程峰值 footprint **11.8 GB**，机器 16 GB；`swap 3279M/4096M`、`Pages wired ≈5.6 GB`（Metal/内核不可换出）→ **swap 打满才是"卡一下"的真因**。
- **磁盘不是瓶颈**：外置固态 USB 5 Gb/s、顺序读 403 MB/s；运行时读盘量主菜单 0 MB/s、游戏内 4–20 MB/s、着色器准备 26 MB/s，全程占带宽 1–6%。换内置 NVMe 不会更快。

**还能做的**：关掉其它吃内存的 App（收益最大）、内存模式选「省内存」、锁帧 30 求"绝对均匀"、分辨率可以上 1080p（GPU 有余量）。

**内存构成（`footprint` 实测，8.26 GB 时点）**：

| 分类 | 占用 | 能不能压 |
|---|---|---|
| IOAccelerator（Metal 显存） | 2483 MB | 能 —— 内存模式压的就是这块 |
| MALLOC_SMALL（UE 堆） | 1645 MB | 不能 |
| WINE_RESERVE | 1395 MB | 不能 |
| untagged VM_ALLOCATE | 1373 MB | 不能，随载入内容增长 |
| Rosetta JIT + Generic + IndirectBranch | 629 MB | 不能 |
| MALLOC_TINY / MEDIUM | 597 MB | 不能 |

**能被参数压下去的只有第一行**，其余 9 GB 是 UE 堆 + Wine + Rosetta 的固定成本。
所以"大幅降内存"做不到；面板的三种内存模式实测能省几百 MB 量级。
启动器自身只占 21 MB（启动后释放 UI 掉到 10 MB），不是内存问题的来源。

## 第 11 节 · 全屏与鼠标锁定（2026-10-29 实测）

### 11.1 全屏模式怎么选（2026-10-29 更正）

**结论：这套 Wine/D3DMetal 下，任何全屏都会闪 / 黑屏，只能用窗口模式。**

| 模式 | 结果 |
|---|---|
| **窗口（唯一稳定）** | 稳定，带标题栏 |
| 无边框全屏 | **会闪 / 黑屏**（D3DMetal 全屏交换链问题） |
| 独占全屏 | **会闪 / 黑屏** |

启动器已强制 `-windowed`（`hl_launcher.m` 的 `argv`），**不要**在游戏里再切全屏。
窗口分辨率由游戏自己的 `SavedUserOptions.sav` 决定（实测 1600x900），
`GameUserSettings.ini` / `-ResX` 不一定压得住。

### 11.2 菜单栏 / Dock 为什么会被划出来

Wine 的全屏窗口在 **layer 26**，旧版 `hl_mouse` 只找 layer 0 → 找不到 → 不锁光标 →
光标自由 → 划到边缘触发菜单栏/Dock（看起来像“闪”）。

### 11.3 hl_mouse 现在的行为

- 找游戏 PID 的**任意 layer** 窗口，取面积最大的。
- 锁定：`CGAssociateMouseAndMouseCursorPosition(false)` + `CGDisplayHideCursor`。
- 钳制 = **窗口 ∩ 屏幕**，四周留 8px；越界只钳到最近的边，**不甩回中心**。
- 按 `0` 解锁/锁回。
- **不要**为了全屏去把 Dock/菜单栏设成自动隐藏（会改用户桌面，且没必要）。

### 11.4 光标被锁死 / 看不见

`hl_mouse` 收到 SIGTERM/SIGINT/SIGHUP 会先解锁，**别用 `kill -9`**。
锁死了就执行：

```c
CGAssociateMouseAndMouseCursorPosition(1);
CGDisplayShowCursor(kCGDirectMainDisplay);   // 多调几次
```

或 `killall Dock; killall Finder` 重启桌面。

### 11.5 人物外观 mod（GitHub / Nexus）

- **GitHub 几乎没有外观 mod**：主要是工具/修改器（`UE4SS-RE/RE-UE4SS`、`Lyall/HogwartsLegacyFix` 超宽屏修复），以及法术解锁/作弊仓库（注意风险）。
- 外观 mod 去 **Nexus Mods** 或 **3DM Mod站**：
  - `https://www.nexusmods.com/hogwartslegacy`
  - `https://mod.3dmgame.com/HogwartsLegacy`
- 安装路径（Mac/Wine 版）：

  ```
  …/drive_c/Hogwarts Legacy Complete/Phoenix/Content/Paks/~mods/
  ```

  没有 `~mods` 就新建；放 `.pak`（配套 `.ucas`/`.utoc` 一起）。
- **优先纯 pak mod**（外观/服装/发型），不需要 UE4SS。
- UE4SS 类（LogicMods）要 DLL 注入，在 Wine + D3DMetal 下**不保证能用**，一次只装一个测。
- 示例：`Keep Appearance - Transmog Stays`（Nexus 2595，无需 UE4SS）、`Equipable 3D Beards`、`Victorian Hair/Outfit Modpack`、`Black Valerie Jacket`、`Custom Makeup Overhaul`。
- 装前备份 `SaveGames/`；出问题删对应 `.pak` 即可。

## 第 12 节 · 怎么判断一个 mod 能不能用（2026-10-30）

### 12.1 先搞清版本坐标：v1613387 就是官方最新版

这点以前搞错过，记下来别再错：

- `v1613387` 对应 **Steam BuildID 20773316**，是官方 **2025-12-03 的 PC 热修**
- 这一版的核心内容就是**修 Mod 系统**（官方在此之前给 PC 加了原生 Mod 支持）
- 所以「mod 不兼容」不是游戏太旧，而是**老 mod 太老**：Tifa 826 / Draco / Emma 都是
  2023 年首发版做的，中间隔了两年多、十几次内容更新

**推论：没有「升级游戏就能用老 mod」这条路，只有「找匹配这个版本的 mod」。**

### 12.2 这版自带官方 CurseForge mod 支持

主 exe（`Phoenix/Binaries/Win64/HogwartsLegacy.exe`，450 MB）里能查到：

```
/Script/GameModManagerShim
CurseForgeLinked
m_curseForgeLink
WBPNCurseForgeSilentAuthTokenResponse
```

也就是说游戏内有官方 Mod 浏览器（走 CurseForge），里面装的 mod 是**按版本自动匹配**的，
比手动往 `~mods` 丢 `.pak` 稳得多。⚠️ 但它是网页组件，Wine 下能不能正常打开要实测。

### 12.3 Nexus 没有「游戏版本」筛选，用这三个判据代替

Nexus 只有部分游戏提供 version 过滤，霍格沃茨之遗没有。所以只能靠：

| 判据 | 怎么用 |
|---|---|
| **更新时间** | v1613387 = 2025-12-03。**只有 2025-12 之后更新的 mod 才可能匹配**；2023–2024 的基本都废了。Nexus 可以按 `Last updated` 排序 |
| **作者说明里的 patch 号** | 有些作者会写 "for 1.0.0.1613387" |
| **文件类型** | 纯 legacy `.pak` 跨版本兼容性好一些；`.ucas/.utoc`（IoStore）必须版本精确匹配 |

### 12.4 下载后用 `_build/check_mod.py` 预检（10 秒出结论）

```sh
cd "/Volumes/SSD/Game/游戏构建/霍格沃茨之遗/_build"
python3 check_mod.py ~/Downloads/某个mod.rar        # 压缩包直接喂进去，自动解开
python3 check_mod.py ~/Downloads/某mod文件夹/
python3 check_mod.py ~/Downloads/*.zip
```

它读文件头就能给出「类型 / 风险 / 结论」，**不用启动游戏**。判定依据：

| 类型 | 风险 | 说明 |
|---|---|---|
| `LUA` | **不可用** | 形态是 `Scripts/main.lua` + `enabled.txt`。要 UE4SS 才跑得起来，而主 exe 里搜 `main.lua` / `enabled.txt` / `ue4ss` **全是 0 命中**——游戏本体根本没有 Lua 加载器，官方 mod 系统只认 `*.pak`（exe 里是 `EModsDirectoryMode::CFCore / Flat / None`） |
| `HEADS` | 看日期 | 头部网格替换。**2025-12-03 之前上传的必崩**（Tifa 826 / Draco / Emma 全是）；之后上传的是当前版本做的，可试 |
| `HAIR` | 看日期 | 同上 |
| `CLOTHING` | 低 | 服装类，不碰头部骨骼，实测可装（Champions Leggings） |
| `DATA` | 中 | 替换 `PhoenixShipData.sqlite`，**同时只能存在一个**（UE 整份覆盖，不合并） |
| `UI` / `SCRIPT` / `CONFIG` | 低 | 准星、蓝图、ini，跨版本安全 |

> **日期怎么来的**：脚本从 Nexus 下载文件名里取——`…-2399-1-0-1766549757.zip` 结尾那 10 位是
> epoch，`… 2595 1.0.2 2026-10-27T21-41Z.zip` 中间那段是 ISO 日期。取不到就退回文件修改时间。

还会额外报三种「装了等于没装」的情况：

- **挂载点不对**：写成 `MyProject/`、`Hermione_Wand/` 这类 → 游戏永远读不到
  （实例：哈利波特法杖）
- **legacy pak 的 Offset 写成 0**：数据实际在 53 字节后 → 读到的是文件头
  （实例：负重999、alohomora、UnlockAllSpells、Free_Gear_Upgrade）
- **没有索引的坏包**：`zzz_UnlockGearLimit_P.pak` 就是，8835292 字节但尾部全 0

**它不能判什么**：不能 100% 预测不崩（资源结构变化读不出来）。但它能筛掉
**头部/发型类**和**坏包**——这两类正是之前所有闪退的来源。

### 12.6 数据库类 mod 为什么「装了没反应」（2026-10-31 定位）

所有 8.8 MB 的 pak 都在替换**同一个文件** `Phoenix/Content/SQLiteDB/PhoenixShipData.sqlite`。
UE 对同路径资源是**整份覆盖、不合并**，所以同时装多个只有**字母序最后**的那个生效。

当时的现场（7 个都在，按挂载顺序）：

```
1. Free_Gear_Upgrade.pak            未压缩 ← Offset 坏
2. InfiniteCasting.pak              压缩   ← 格式正确
3. UnlockAllSpells.pak              未压缩 ← Offset 坏
4. alohomora_unlocked_p.pak         未压缩 ← Offset 坏
5. z_RORUpgradoV3_P.pak             未压缩 ← Offset 坏
6. zz_AcceleratedAlchemy_0CD_P.pak  压缩   ← 格式正确
7. zz_Broomunlocktest_P.pak         未压缩 ← Offset 坏   ← 它赢了
```

**赢的那个恰好是坏包**：`Offset` 写成 0，数据实际在 53 字节之后。按游戏的读法
（从 Offset 读 8835072 字节）打开，SQLite 直接报 `file is not a database`。
读失败 → 游戏退回原版数据库 → **所有数据库 mod 一起失效**，表现就是「技能无冷却装了没用」。

**判据（离线就能查，不用启动游戏）**：

```sh
python3 - <<'PY'
import sys, sqlite3
sys.path.insert(0, "/Volumes/SSD/Game/游戏构建/霍格沃茨之遗/_build")
from pakfull import read_pak
p = "<某个 pak>"
pk = read_pak(p); e = pk['entries'][0]
open("/tmp/_t.sqlite","wb").write(pk['data'][e['offset']:e['offset']+e['size']])
print(sqlite3.connect("/tmp/_t.sqlite").execute("PRAGMA integrity_check").fetchone())
PY
```

**修法**：只留**一个**数据库 pak，而且必须是格式正确的（压缩格式，块坐标是绝对偏移）。
实测 `InfiniteCasting.pak` 就是好的——解压出来 529 张表、`integrity=ok`、
162 个法术里 **72 个 `CooldownTime` 被改成 0**（Accio / Confringo / AvadaKedavra / Crucio / Depulso …）。

```sh
# 只留技能无冷却，其余数据库 mod 全部移出 ~mods
mkdir -p "$GAME/Paks_mods_disabled/_sqlite_other"
mv "$MODS"/{Free_Gear_Upgrade.pak,UnlockAllSpells.pak,alohomora_unlocked_p.pak,\
z_RORUpgradoV3_P.pak,zz_AcceleratedAlchemy_0CD_P.pak,zz_Broomunlocktest_P.pak} \
   "$GAME/Paks_mods_disabled/_sqlite_other/"
```

> **想换别的效果**：一次只留一个，把它改名成 `zzzz_<名字>.pak` 保证它排序最后。
> 想同时要多个 → 只能合并数据库，但**手动合并这条路试过两次都崩**（见下），别再走。
>
> **合并为什么失败**：用「多数投票」把 20 个 mod 的数据库合并（排除跨版本的
> `z_RORUpgradoV3_P`），`PRAGMA integrity_check` 通过、关键值抽查也对，
> 但装上去一进文字界面就闪退。这些库不是「原版 + 改几行」的干净差异，投票合出来的库游戏不接受。

| 画面档 流畅 / 均衡 / 清晰 | `GameUserSettings.ini` 的 `sg.*`（全 0 / 1 / 2）；流畅档另外在 `Engine.ini` 关掉阴影、SSR、体积雾、AO、景深、动态模糊、泛光、镜头光晕、色散 |

## 第 6 节 · 坑位清单（按"卡住时间"排序）

1. **原厂启动器在 macOS 15 上必挂**：`KegworksSdk.FileUtilsError error 1`，窗口闪退、日志空白。
   这不是配置问题，只能换启动器（3.4 节）。霍格沃茨那份文档里同款（当时叫 `SikarugirSdk`）。
2. **`libinotify` 断链**：复制到别的目录后 `dyld: Library not loaded: @rpath/libinotify.0.dylib`。
   原厂 dmg 里 `wine/lib/` 本来就没这个文件，靠 `DYLD_FALLBACK_LIBRARY_PATH` 兜着；
   一旦环境变量没给到就直接死。**根治办法是建符号链接**（3.3 ①）。
3. **`com.apple.quarantine`**：从 dmg 拷出来的 app 双击报「已损坏，无法打开」。`xattr -dr` 清掉即可。
   注意清完 `open -a` 才能起来，否则会一直弹这个框并把启动卡在那里。
4. **游戏退出时会重写 `GameUserSettings.ini`**，而且只留一个 `[Internationalization] Language`。
   也就是说**手改画质设置活不过一局**。面板的做法是每次启动前重写 —— 别去改那个文件，改面板。
5. **不能直接 `wine <exe> -windowed` 起游戏**。实测这种起法有相当大概率静默退出（进程没了、没窗口、没日志）。
   必须用 `wine explorer /desktop=PHK,<尺寸> <exe>` 包一层，装上启动器后连续 6 次启动 6 次成功，
   出窗口耗时 15~25 秒。
6. **`t.MaxFPS` 这个游戏不认**。写进 `Engine.ini` 照样跑到 96 fps。**锁帧只能用 VSync**
   （`bUseVSync=True`，显示器 60 Hz 就锁在 60）。实测锁上之后帧时间曲线是平的（60.00 [60.00, 60.00]）。
7. **虚拟桌面同名会复用旧尺寸**。`/desktop=PHK,1024x576` 在 `PHK` 已经存在时**不生效**，
   窗口还是上一次的尺寸。所以分辨率必须同时写进 `GameUserSettings.ini`，别只靠命令行参数。
8. **`DYLD_FALLBACK_LIBRARY_PATH` 少了 `Contents/Frameworks`** → 字体库和 inotify 都找不到，
   表现为窗口塌成 0 尺寸或者 dyld 直接报错。这是霍格沃茨那份文档里折腾最久的坑，同款。
9. **`WINE_CPU_TOPOLOGY` 不能省**，否则启动阶段容易崩。
10. **prefix 里的用户名是 `Kegworks`**，不是 macOS 用户名。找配置/存档时写死它。
11. **强杀游戏会留下 wine 服务和 `winedevice.exe` 进程**，它们占着 prefix，下次启动就卡住。
    清理：`pkill -9 -f "Paranormal HK.app/Contents/SharedSupport"` + `wineserver -k`，然后**等 2~3 秒**再起。
12. **Rosetta 2 必须先装**。整个 Wine 是 x86_64 薄二进制，没 Rosetta 连 `wine --version` 都跑不起来。
13. **`Info.plist` 里的名字是打包者的**：`CFBundleName = 割麦网`、`CFBundleShortVersionString = ☇ 割麦网 | www.getmacapp.com`。
    菜单栏和程序坞会显示「割麦网」。改法：
    ```sh
    P="$APP/Contents/Info.plist"
    /usr/libexec/PlistBuddy -c "Set :CFBundleName 港诡实录" "$P"
    /usr/libexec/PlistBuddy -c "Add :CFBundleDisplayName string 港诡实录" "$P"
    /usr/libexec/PlistBuddy -c "Set :CFBundleShortVersionString 1.04" "$P"
    ```
    改完 app 的签名封印会失效，但本机（已清 quarantine、ad-hoc 签名）实测照常运行；
    真要保险就重新签名：`codesign --force --sign - "$APP/Contents/MacOS/Kegworks"`。
14. **UE4 Shipping 版没有控制台**，`stat fps` 用不了。想看帧率只能开 `MTL_HUD_ENABLED=1`，
    HUD 会显示 FPS / Pre（CPU 帧时间）/ GPU / Mem，并且**只在游戏窗口内部**，屏幕截图要对着窗口抓。
15. **内存压到 1.5 GB 就到底了**。这 1.5 GB 是 Wine + Rosetta + UE4 堆的固定成本；
    把纹理池从 1000 压到 128、渲染分辨率打 85%，总共只再省十几 MB —— 真正的内存在引擎堆里，不是纹理。
16. **`open -a` 只会"激活"已经在跑的启动器**，不会重新走一遍启动流程。
    所以写脚本自动开游戏时，`autoplay` 标记必须配一次「把启动器本体也杀掉」：
    ```sh
    pkill -9 -f "Paranormal HK.app/Contents"     # 注意是 Contents，不是 Contents/SharedSupport
    ```
    只杀 wine 进程的话，`touch autoplay && open -a` 会静默什么都不发生（本机踩过，三次全"失败"其实是没启动）。

## 第 9 节 · 性能基线与调优边界

**实测数据（MacBook Air M4 / 16 GB，macOS 15.6，2026-10-29）**：

| 配置 | 分辨率 | FPS | Pre（CPU） | GPU | Mem |
|---|---|---|---|---|---|
| 原版默认（未改任何 ini） | 1280×720 | **35.5** | 28.15 ms | 18.40 ms | 1.84 GB |
| 原版默认 | 1920×1080 | **27.8** | — | 35.57 ms | — |
| 流畅，不锁帧 | 1280×720 | **84.1** | 11.89 ms | 8.26 ms | 1.59 GB |
| 流畅 + 省内存，不锁帧 | 1280×720 | 75.3 | 13.28 ms | 9.56 ms | 1.58 GB |
| 流畅 + 极省 + 85% 渲染 | 1920×1080 | 78.5 | 12.73 ms | 8.53 ms | 1.62 GB |
| **流畅 + 省内存 + VSync 60（面板默认）** | 1280×720 | **60.00 稳定** | 16.67 ms | 9.96 ms | **1.58 GB** |
| 流畅 + 极省 + VSync 60 | 1280×720 | 60.00 稳定 | 16.67 ms | 8.39 ms | 1.57 GB |

**瓶颈判断（决定哪些优化有用）**：

- 原版默认掉到 35 fps 时，**CPU 侧 28 ms 是主因**，GPU 只要 18 ms。降分辨率救不了——降画质档才能，
  因为它砍的是阴影/后处理这些**每帧都要翻译的命令**，Rosetta 少翻译一层，帧时间直接腰斩。
- 关掉这些之后 GPU 只剩 8~10 ms，**60 fps 有充足余量**，所以面板默认用 VSync 锁 60：
  帧时间曲线是平的（`60.00 [60.00, 60.00]`），机器不烫、风扇不转，比"跑 84 fps 抖着"舒服得多。
- **内存 1.5 GB 是底**。构成大致是：Wine + Rosetta 固定开销 ≈ 0.9 GB，UE4 堆 + CEF ≈ 0.5 GB，
  Metal 纹理 ≈ 0.1~0.2 GB。纹理池 1000→256、mip 偏置、85% 渲染加起来只省十几 MB，
  所以「内存压力」这一项的实际收益是**让长时游玩的池子不继续涨**，不是立刻省下几百 MB。

**还能做的**：关掉其它吃内存的 App；分辨率可以上 1080p（GPU 有余量，`极省` 档在 1080p 也能 78 fps）；
想更省电就把帧率设 30。

> 未验证项：帧率上限的「30」档只写了配置，没有单独实测；1080p 长时游玩（>30 分钟）也没测。

## 第 1 节 · 这个包是什么

| 项 | 值 |
|---|---|
| App | `/Volumes/SSD/Game/DMC4/Devil May Cry 4.app`（27 GB） |
| 可执行 | `prefix/drive_c/Program Files (x86)/Devil May Cry 4 Special Edition/DevilMayCry4SpecialEdition.exe` |
| 位宽 | **PE32 / i386（32 位）**，`machine=0x014c`，15.8 MB |
| 图形接口 | **只有 D3D10**（直接导入 `d3d10.dll`），`nativeDX10/` 资源 25 GB，**没有 DX9 回退路径** |
| Wine | `KegworksCX 24.0.7 (revision 0)` = Wine 9.0，x86_64 薄二进制 + Rosetta 2 |
| 渲染链路 | `d3d10.dll` → wined3d → Vulkan → **MoltenVK**（`MOLTENVKCX=1`） |
| 启动器 | 原厂 Kegworks 面板，`open -a` 启动正常（直接跑 `Contents/MacOS/Kegworks` 会报 `FileUtilsError error 1`） |

**为什么只能走 D3D10**：游戏本体只带 `nativeDX10`，D3D9 路径被删了。
所以「改用 DXVK 的 d3d9」这条路不存在。

## 第 2 节 · 当前最佳配置（定版）

### 2.1 `Contents/Info.plist`（决定后端）

| 键 | 值 | 说明 |
|---|---|---|
| `D3DMETAL` | `1` | 原厂默认 |
| `DXMT` | `0` | 关 —— DXMT 的 32 位 DLL 在这个 Wine 上装不进去（第 7 节） |
| `DXVK` | `0` | 同上 |
| `D9VK` | `0` | 游戏没有 DX9 路径，开了也没用 |
| `MOLTENVKCX` | `1` | **必须有**：wined3d 走 Vulkan 就靠它接到 MoltenVK |
| **`METAL_HUD`** | **`0`**（交付值） | 排障时改 `1`，右上角出 FPS/Pre/GPU/Mem |
| **`FASTMATH`** | **`1`** | MoltenVK 快速数学（`MVK_CONFIG_FAST_MATH_ENABLED`），降低着色器 ALU 开销；已实测不破坏画面 |
| **`CLI Custom Commands`** | `export LANG=zh_CN.UTF-8; cp -f "<_build>/config.ini" "<prefix>/…/config.ini"` | **启动前自动写回定版画质**，双击 app 也能生效（解决 `TextureDetail` 被回写 HIGHEST 的老问题） |
| `WINEDEBUG` | `-plugplay,+loaddll` | 原厂默认，别改成 `-all` |

> ⛔ **绝对不要设 `WINE_D3D_CONFIG=renderer=gl`**。
> 那条会把 wined3d 赶到 OpenGL：帧率掉到 8 fps，而且**所有人物变全黑剪影**。

改 HUD 开关：

```sh
A="/Volumes/SSD/Game/DMC4/Devil May Cry 4.app"
plutil -replace METAL_HUD -string 1 "$A/Contents/Info.plist"   # 开
plutil -replace METAL_HUD -string 0 "$A/Contents/Info.plist"   # 关
```

### 2.2 `config.ini`（最低画质定版）

路径：`prefix/drive_c/users/Kegworks/AppData/Local/CAPCOM/DEVILMAYCRY4SPECIALEDITION/config.ini`

```ini
[GRAPHICS]
HDR=DEFAULT
AntiAlias=NONE
AltAntiAlias=NONE
DeferredLightingLight=MONOCHROME_SPECULAR
DeferredLightingHDR=INTEGER_LOG
SLI=OFF
GodRay=OFF
Stereo=OFF
EffectVolume=LOW
TextureResolution=0
Quality=0
FrameRate=2
TextureDetail=LOW
TextureMipLimite=2
[DISPLAY]
Resolution=1024x576
Aspect=DEFAULT
RefreshRate=60.00Hz
FullScreen=OFF
VSYNC=OFF
[CPU]
JobThread=4
RenderingThread=ON
```

**合法枚举值全表**（从 exe 里 `strings -a -t d` 挖出来的，写错会被静默丢弃并回写默认）：

| 配置项 | 合法值（exe 里的完整形式 → 写入 ini 时**去掉前缀**） | 定版 |
|---|---|---|
| `DeferredLightingLight` | `DL_LIGHT_MONOCHROME_SPECULAR` / `DL_LIGHT_APPROXIMATE_SPECULAR` / `DL_LIGHT_SEPARATE_SPECULAR` | `MONOCHROME_SPECULAR`（最便宜） |
| `DeferredLightingHDR` | `DL_HDR_INTEGER` / `DL_HDR_FLOAT` / `DL_HDR_FLOAT_PRECISION` / `DL_HDR_INTEGER_LOG` | `INTEGER_LOG` |
| `TextureDetail` | `TEXDETAIL_LOWEST` / `TEXDETAIL_LOW` / `TEXDETAIL_MEDIUM` / `TEXDETAIL_HIGH` / `TEXDETAIL_HIGHEST` | `LOW` |
| `HDR` | `HDR_DEFAULT` / `HDR_FLOAT` | `DEFAULT` |

> **写法要点**：ini 里的值是**去掉前缀**的。exe 枚举叫 `DL_LIGHT_MONOCHROME_SPECULAR`，
> ini 里就写 `MONOCHROME_SPECULAR`。此前试的 `UNLIT`、`TextureDetail=0` 被丢弃，
> 就是因为它们压根不在枚举里。
>
> ⚠️ **`TextureDetail` 会被游戏回写成 `HIGHEST`**（实测每次退出 config 都被改回去）。
> 所以最低画质**必须在每次启动前重新写入**，否则从来没真正生效过。
> `_鼠标操作.sh` 已内置这一步（启动前 `cp` 一次定版 config.ini）。
> 详见第 6 节坑位 25。

其余要点：

- `Quality=0` 是最低档；`TextureResolution=0`、`EffectVolume=LOW` 是单项最低。
- `TextureMipLimite` 写 `0` 会被游戏**回写成 2**（说明 0 不合法）。别再试。
- 分辨率**可以写任意值**（`960x540`、`1024x576` 都实测生效，窗口会跟着变）。

### 2.3 注册表（**这是帧率翻倍的关键**）

`prefix/user.reg` → `[Software\\Wine\\Direct3D]`：

```
"VideoMemorySize"="4096"
"csmt"="3"
"OffscreenRenderingMode"="fbo"
"renderer"="vulkan"
```

原厂这一节是**空的**，wined3d 用自动探测的显存值（偏小），导致纹理每帧被反复换出。
改成 `4096` 后同一场景帧率 **19.9 → 40 fps**，`Mem` 从 2.16 GB 降到 1.5~1.7 GB。

改注册表**必须先退出游戏和 wineserver**，否则会被覆盖回写：

```sh
pkill -9 -f "Devil May Cry 4.app"; pkill -9 -f DevilMayCry4; pkill -9 -f wineserver; sleep 3
# 然后才能编辑 user.reg
```

## 第 4 节 · 性能优化实操（怎么从 15 fps 救到 50 fps）

按收益从大到小排，前两条就能救回来：

| # | 动作 | 收益 | 代价 |
|---|---|---|---|
| 1 | 注册表 `VideoMemorySize=4096` | **+100%**（19.9 → 40 fps） | 无 |
| 2 | `Resolution=1024x576` | **+25%**（40 → 50 fps） | 画面变软 |
| 3 | `Quality=0` + 三个单项最低 + `GodRay=OFF` | +10~20% | 特效变少 |
| 4 | `Resolution=960x540` | 只再 +4% | 更糊，**不建议** |
| 5 | `JobThread=9 → 4` | 减少线程争抢，波动变小 | 无 |

**没用的动作**（别浪费时间）：

- ❌ 关垂直同步（本来就 `VSYNC=OFF`）
- ❌ 继续降分辨率到 540p 以下 —— 低于 540p 后 GPU 已经不是瓶颈
- ❌ 换 `renderer=gl` —— 画面直接废掉
- ❌ 加 DXVK / DXMT —— 32 位 DLL 根本装载不进去（第 7 节）
- ❌ 改 `DeferredLightingLight` / `TextureMipLimite` —— 非法值会被静默丢弃

**为什么低分辨率收益越来越小**：GPU 时间从 23.6 ms 降到 ~11 ms 之后，
每帧剩下的 ~9 ms 是 wined3d 的绘制调用翻译 + Rosetta 翻译，跟像素数无关。
所以 **1024x576 是甜点**，再降只是变糊。

## 第 5 节 · 实测数据（2026-10-29）

Metal HUD 读法：**`FPS:` 那行就是帧率，`Pre:` 是每帧毫秒，两者互为倒数**（`1/0.0210 = 47.6`）。
`GPU:` 是 GPU 毫秒。别把 `FPS:` 当成毫秒读，会得到完全相反的结论。

**怎么量（不用肉眼看 HUD）**：`_build/` 里有 `ocr.m` + `hudread.sh`，
用 macOS Vision 把 HUD 数字直接解析出来：

```sh
cd "/Volumes/SSD/Game/游戏构建/鬼泣4/_build"
clang -O2 -fobjc-arc -o ocr ocr.m -framework Vision -framework AppKit -framework Foundation
./hudread.sh <窗口ID> 5 2        # 抓 5 张、每张间隔 2s，自动打出 FPS/GPU/Mem
```

前提 `METAL_HUD=1`。窗口 ID 用 `./winid | grep -i CRY` 取。
> ⚠️ **A/B 对比必须用同一机位**。换场景时的帧率差异会完全盖过画质设置的差异，
> 本次就因此差点得出「最低画质反而更卡」的错误结论（两边其实不在同一场景）。
> 要严格对比就进游戏内置 **Benchmark**（固定镜头路径，可重复）。

| 场景 | 分辨率 | 画质 | FPS | GPU ms | 备注 |
|---|---|---|---|---|---|
| 剧院广场 · 强光固定机位 · 优化前 | 1280x720 | 最低 | **16~20** | 23~44 | 注册表没写显存 |
| 剧院广场 · 强光固定机位 · 定版 | 1280x720 | 最低+单色镜面 | **16.5** | 39.7 | 加了注册表也没救回来 |
| 剧院广场 · 强光固定机位 · 定版 | 800x450 | 最低+单色镜面 | **19.5** | 37.5 | **降分辨率几乎无效** |
| 室内走廊 / 楼梯 | 1280x720 | 最低 | 23~27 | 27~32 | 比广场好些 |
| 看天空的空旷视角 | 1024x576 | 最低 | 48~53 | ~11 | 便宜视角，不能代表战斗 |
| 预渲染过场视频 | 1280x720 | 默认 | 118~122 | 2.4 | 视频解码，与 3D 性能无关 |

> ⚠️ **表里"看天空 48~53 fps"不能当作可玩性依据**。早期我是在人物往前走、镜头对着天空的
> 便宜视角测的，那个数字严重乐观。**真实战斗/强光场景是 16~20 fps。**

- 内存占用：优化前 2.16 GB → 优化后 **1.47~1.70 GB**
- `DeferredLightingLight` 实测有 **3 个合法值**（从 exe 里挖出来的枚举 `DL_LIGHT_*`）：
  `SEPARATE_SPECULAR` / `APPROXIMATE_SPECULAR` / **`MONOCHROME_SPECULAR`**。
  定版用最便宜的 `MONOCHROME_SPECULAR`，游戏**接受并保留**（不会像 `UNLIT` 那样被丢弃）。
- **瓶颈结论（修正版）**：
  - 强光场景里 GPU 独占 37~40 ms，而把分辨率从 720p 降到 450p 只快了 18%
    → **大头是阴影/延迟光照这类「与屏幕像素无关的固定开销」**，降分辨率救不回来。
  - 轻场景（室内、空旷）GPU 掉到 11~27 ms，此时才轮到分辨率说话。
  - 所以 **1024x576 是折中定版**；想再快一点可以用 800x450，但只多 18%，画面明显变糊。
  - 想真正解决强光场景，只能绕开 wined3d 的绘制调用翻译层；而 DXVK/DXMT 装不进来（第 7 节），
    **这套环境的天花板就在这里**。

**鼠标化操控实测验证（2026-10-29，v4 重映射器）**

判据：截图做像素差分，**无操作噪声底仅 0.84**，任何动作都远超它。

## 第 6 节 · 坑位清单

1. **只有 DX10，没有 DX9** —— DXVK/d9vk 路线直接不存在。
2. **`d3d10.dll` 不能删** —— 游戏直接导入，删了报 `d3d10.dll not found`。
3. **`wineboot -u` 会覆盖 `syswow64` 里的原生 DLL**（实测 1809141 → 208910 字节）。别跑。
4. **手工 `wine` 启动必弹 `D3D10 create failed`** —— 启动器会做后端部署和预处理，
   手工命令不会。**一律用 `open -a` 启动。**
5. **`open -a` 不要在游戏启动后重复调用** —— 它会激活 Kegworks 启动器本体而不是 wine 窗口，
   游戏丢掉 key window 后**再也拿不回焦点**（键盘全失效）。要抢焦点就点窗口标题栏。
6. **窗口坐标换算**：`winid` 报的是真实点坐标（如 `1024x604 @ 35,33`，含 28 px 标题栏）。
   截图预览常被缩放显示，**别拿预览图上的坐标去点击**，差 1.78 倍。
7. **`renderer=gl` 会在 8 fps 下把人物渲染成全黑剪影** —— 一定要走 Vulkan/MoltenVK。
8. **`config.ini` 每次退出都会被游戏重写** —— 非法值会被静默改回默认。改之前先退游戏。
9. **`TextureMipLimite=0` 不合法**，会被回写成 `2`。
10. **配置项的值必须是 exe 枚举里的合法值**，写 `UNLIT` 之类会被静默丢弃并回写默认。
    完整枚举表见 2.2 节。**写入 ini 时要去掉前缀**（`DL_LIGHT_*` / `DL_HDR_*` / `TEXDETAIL_*`）。
11. **键盘被输入法吃掉**：中文输入法下 Enter/ESC 会被 IME 拦（`macdrv_ImeProcessKey`），
    表现为「按了没反应」或「按任何键都变成下移」。切成 ABC 英文键盘就好，见第 8 节。
12. **`METAL_HUD=1` 会一直显示右上角数字**，交付前记得改回 `0`。
13. **32 位 WoW64 路径**：这是它比港诡实录（64 位）慢得多的根本原因，不是配置问题。
14. **强光场景降分辨率基本无效**：GPU 37~40 ms 是阴影/延迟光照的固定开销，720p→450p 只快 18%。
    别指望靠降分辨率救强光广场。详细数据见第 5 节。
15. **`DeferredLightingLight` 合法值只有三个**（从 exe 枚举 `DL_LIGHT_*` 挖的）：
    `SEPARATE_SPECULAR` / `APPROXIMATE_SPECULAR` / `MONOCHROME_SPECULAR`。定版用 `MONOCHROME_SPECULAR`。
16. **合成按键绝不能写 `kCGEventSourceUserData`**：赋非零值会被系统当无效事件丢弃（第 9.4 节）。
17. **点按时长必须 ≥ 1 帧**（≥60 ms，稳妥用 120~160 ms）。游戏 16~25 fps，短按会被整帧漏掉。
18. **不要在事件拦截回调里 `usleep`**：自己发的事件会被挤到一起送达，等于没按。
19. **窗口列表里可能混进 28×36 的辅助窗口**：按窗口号抓图时要挑标题是
    `DEVIL MAY CRY 4 Special Edition` 的那个，`head -1` 容易抓错。
20. **鼠标视角判定不能用单次事件 delta**：慢移时每次 delta 只有 1，永远达不到死区阈值，
    表现是"视角完全不跟手"。要**累积位移**，停手后衰减释放方向键。
21. **前台判断必须缓存**：鼠标每秒上百条移动事件，每次全量遍历窗口列表会吃满 CPU。
    定版 200 ms 刷新一次。
22. **必须用 `kCGEventSourceUnixProcessID == getpid()` 放行自家合成事件**：
    否则 `Shift→空格` 会被自己的 `空格→K` 二次改写，锁定变成跳跃。
23. **鼠标捕获退出必须还原 `CGAssociateMouseAndMouseCursorPosition(1)`**：
    `atexit` 不覆盖 `SIGTERM`，被 `pkill` 杀掉会漏，光标会一直解耦像坏了一样。
24. **测试工具把鼠标事件位置写成 `(0,0)` 等于瞬移光标到原点**，
    会被误判成"捕获失效"。模拟相对移动要保持位置不变、只写 delta。
25. **`TextureDetail` 每次退出都会被游戏回写成 `HIGHEST`**（实测）。
    只在装机时写一次最低画质**从来没真正生效过**——必须在每次启动前重新写入。
    `_鼠标操作.sh` 已内置这一步。同理 `TextureMipLimite=0` 会被回写成 `2`。
26. **`./swic` 不带参数只是列出输入法清单，不会切换**。必须 `./swic keylayout.ABC`。
    切不掉中文输入法时 Enter/ESC 全被 IME 吃掉，表现为"菜单按不动"，
    会让人误以为游戏卡死或键位失灵（本次就是这么在标题画面卡了很久）。

## 第 7 节 · 为什么不用 DXVK / DXMT（别再试了）

这两个是唯一能让 Metal 直接跑 D3D 的方案，理论上快很多，但**在这个 Wine 上装不进去**。

- 现象：把 DXMT 的 32 位 `dxgi.dll` / DXVK 的 32 位 `d3d11.dll` 放进游戏目录或
  `syswow64`，游戏一律报 `d3d10core.dll not found`（`c0000135`）。
- 根因（读了 `dlls/ntdll/loader.c` 定位）：`open_dll_file()` 里 `NtCreateSection(SEC_IMAGE)`
  **拒绝大映像**。`steam_api.dll`（`SizeOfImage` 405 KB）能映射；
  DXMT `dxgi.dll`（1.37 MB）、DXVK `d3d11.dll`（3.77 MB）全部失败。
- 排除项（全试过，都无效）：ImageBase、FileAlignment、Characteristics、Subsystem、
  TLS 目录、清空导入表、把文件尾部膨胀到 4.5 MB（`SizeOfImage` 不变仍能映射）
  → **是 `SizeOfImage` 本身的硬限制，不是文件大小**。
- 结论：**Kegworks 24.0.7 的 wow64 内核就这么大胃口**，32 位大映像装不进来。
  要上 DXVK/DXMT 只能换 64 位游戏，或者等更新的 Wine 修掉这条限制。

## 第 8 节 · 键盘 / 输入法

**症状**：菜单里回车、ESC 按了没反应；或者按任何键光标都往下走一格。

**原因**：wine 日志里能看到 `macdrv_ImeProcessKey himc 0x20076, scan 0x1c, vkey 0xd`
—— 键码是对的（`vkey 0xD` 就是回车），但被 macOS 的输入法处理链吃掉了。
中文输入法（搜狗拼音 / 系统拼音）状态下必现。

**解决**：切到英文键盘。`Ctrl+Space`，或者用归档里的小工具强制切：

```sh
cd "/Volumes/SSD/Game/游戏构建/鬼泣4/_build"
clang -framework Carbon -o swic swic.c
./swic keylayout.ABC        # 切到 ABC 英文键盘
```

游戏内键位（默认）：方向键移动、`Enter` 确认、`ESC` 暂停/返回。

### 9.3 鼠标化操作（`_build/dmc4_input_v4`，系统层重映射）

游戏本身**不支持鼠标转视角**，也**不给任何键位绑定鼠标**（菜单里改不出来）。
所以只能在系统层拦截鼠标事件，翻译成它认识的按键。

**前提：游戏内键位必须是 Capcom 出厂值**，否则重映射器发的键会被曲解。
被改乱了就进 `SYSTEMS` → 右翻到角色页 → 底部 **`DEFAULT`** 一键复原
（复原后是 `MELEE I / GUN J / JUMP K / BRINGER L / TRIGGER N / LOCK-ON 空格 / EXCEED Q`）。

```sh
bash "/Volumes/SSD/Game/游戏构建/鬼泣4/_build/_鼠标操作.sh"            # NERO（开局角色）
bash "/Volumes/SSD/Game/游戏构建/鬼泣4/_build/_鼠标操作.sh" --melee j  # 但丁 / 维吉尔
bash "/Volumes/SSD/Game/游戏构建/鬼泣4/_build/_鼠标操作.sh" --release  # 光标不跟手时还原
```

| 你的操作 | 实际发给游戏 | 说明 |
|---|---|---|
| **鼠标左键** | `I` 近战（`--melee j` 时是 `J`） | |
| **鼠标右键** | `L` 鬼手 / 风格技 | |
| **鼠标中键 / 侧键 / 键盘 `F`** | `J` 枪（`--melee j` 时是 `I`） | 三个入口任选，方便左手右手 |
| **键盘 左/右 `Shift`** | `空格` 锁定（按住） | Shift 只产生 `FlagsChanged`，没有 KeyDown |
| **键盘 `空格`** | `K` 跳跃 + 确认 | 游戏里确认与跳跃本来就是同一个键 |
| **鼠标移动** | `↑↓←→` 转视角 | 光标**锁在游戏框内**，不会滑出去 |
| 长按 `Cmd` | 放行 | 临时去操作别的窗口 |
| `Ctrl+C` | 退出重映射器 | |

**枪械键为什么这么设计**：近战/鬼手已占左右键，枪械放到**中键 + 侧键 + 键盘 `F`**
—— 中键/侧键在右手拇指区，与左右键形成"近战—枪—鬼手"三角；`F` 是左手备用，
战斗中不用离开 `WASD` 就能开枪。滚轮没绑（游戏用不上，留给系统）。

**鼠标捕获的实现**（这是"视角跟随鼠标 + 光标不出框"的关键）：

```c
CGWarpMouseCursorPosition(窗口中心);        // 光标先钉进窗口
CGAssociateMouseAndMouseCursorPosition(0); // 物理鼠标位移与光标解耦
```

解耦之后，物理鼠标的移动**只产生 delta、不推动光标**，所以光标永远不会滑出窗口；
每 10 ms 再钳制一次，任何来源把光标带出框就拉回中央。
长按 `Cmd` 或切到别的窗口时自动解除，退出时用 `--release` / 信号处理还原
（**必须还原**，否则光标会一直解耦，看起来像鼠标坏了）。

### 9.4 写这类重映射器踩到的六个坑（别再犯）

1. **点按必须 ≥ 1 帧**。游戏只有 16~25 fps，一帧 40~60 ms。
   20 ms 的 keyDown/keyUp 会整段落在两帧之间被完全丢弃，表现是"程序说发了，游戏毫无反应"。
   实测：`I` 用 20 ms 无反应，用 160 ms 立刻挥剑。**定版用 120 ms 最小按住**。
2. **绝不能写 `kCGEventSourceUserData`**。给它赋任何非零值（哪怕是用来做"防自激标记"），
   系统会把事件**当无效事件丢弃**。这是本次最隐蔽的一个坑。
3. **不要在事件拦截回调里 `usleep`**。回调阻塞期间自己 post 的事件会被挤到回调返回后
   一起送达，游戏只看到 1 ms 的按下，等于没按。正确做法：回调里只置标志位，
   在 `CFRunLoopTimer`（10 ms）里真正发送。
4. **必须区分真人输入与自家合成事件**。自己 post 的事件会再次流过自己的 event tap，
   如果不放行，`Shift→空格` 会被 `空格→K` 二次改写，锁定就变成了跳跃。
   判据：`CGEventGetIntegerValueField(ev, kCGEventSourceUnixProcessID) == getpid()`。
5. **视角判定不能用单次事件 delta**。慢速移动时每次 `delta` 只有 1，
   永远达不到死区阈值（6），表现是"视角完全不跟手"。
   正确做法：**累积位移**，超过阈值才转，停手 60 ms 后按 0.6 的比例衰减，
   衰减到阈值以下方向键自然松开。
6. **前台判断必须缓存**。鼠标每秒产生上百条移动事件，
   每次都 `CGWindowListCopyWindowInfo` 全量遍历窗口列表会吃满 CPU 并引入输入延迟。
   **定版 200 ms 刷新一次**。顺带把窗口矩形一起取出来，供捕获时钉光标用。

> 补充坑（鼠标捕获专用）：
> **退出路径必须还原 `CGAssociateMouseAndMouseCursorPosition(1)`**。
> `atexit` 不覆盖 `SIGTERM`，被 `pkill` 杀掉时会漏——必须挂 `signal(SIGINT/SIGTERM/SIGHUP)`。
> 另外测试工具若把事件位置写成 `(0,0)`，等于直接把光标瞬移到原点，会误判成"捕获失效"；
> 模拟相对移动要**保持位置不变、只写 delta**。

### 11.2 真实瓶颈：重场景是 CPU + GPU 双卡

|---|---|
| FPS | **19~25** |
| Pre（每帧总毫秒） | **40~52 ms** |
| GPU | **24~28 ms** |
| 差值（CPU 侧） | **约 15~25 ms** |

- 这个场景 **GPU 24~28 ms、CPU 15~25 ms**，两边都不轻松；

```
    │   ├── ipcserver                 Steam 模拟器的 IPC 服务端
    │   ├── steamclient.dylib         假 steamclient（游戏通过 DYLD 加载它）
    │   └── reset                     原包的 launchd 辅助工具（现在不用）
    ├── Config/
    │   ├── steam_appid.txt           3021100
    │   └── nsteame_settings/         模拟器配置 + applogs.txt
    ├── Resources/
    │   └── load.orig.sh              原版启动器备份（只作对照，别执行）
    └── Game/
        └── MilkGame.app/             ← 内层：真正的 Unity 游戏（31 GB 全在这）
```

外层存在的唯一理由：**在启动游戏之前把三个环境变量塞进去**，这是 Steam 模拟器工作的前提。

```sh
SteamAppId=3021100
SteamGameId=3021100
STEAMEMU_SETTINGS_DIR=…/Contents/Config
DYLD_LIBRARY_PATH=…/Contents/MacOS      # 让游戏找到 steamclient.dylib
```

把内层直接双击是**不行**的——没有这几个变量，游戏会卡在 SteamAPI_Init 然后自己退出。

## 第 3 节 · 从零部署（换 Mac / App 丢了走这里）

前提：固态挂在 `/Volumes/SSD`，`原始包/美女室友竟然.dmg` 在。全程不需要 sudo，不改系统设置。

```sh
cd "/Volumes/SSD/Game/游戏构建/MilkGame/_build"
bash 01_部署.sh
```

脚本做三件事：

1. **只读挂载** dmg 到 `/tmp/fh_mnt`（`-nobrowse`，不弹 Finder 窗口）
2. `cp -Rp` 展开 `MilkGame.app` → `/Volumes/SSD/Game/MilkGame/美女室友竟然.app`（约 31 GB，5–10 分钟）
3. 调 `02_清理与校验.sh` 收尾

> **为什么用 `cp -Rp` 而不是 `ditto`**：ditto 会先把每个文件写成 `.BC.T_xxxxxx` 临时名再改名，
> 一旦改名被拦（受限环境、只读目标），整包会停在一堆临时文件上——而临时名一眼看不出是 31 GB 的正片，
> 清理残留时极易连正片一起删掉。`cp -Rp` 直接落到最终文件名，没有这个坑。

想自己一步步来：

```sh
hdiutil attach -readonly -nobrowse -mountpoint /tmp/fh_mnt "/Volumes/SSD/Game/原始包/美女室友竟然.dmg"
cp -Rp "/tmp/fh_mnt/MilkGame.app" "/Volumes/SSD/Game/MilkGame/美女室友竟然.app"
hdiutil detach /tmp/fh_mnt
bash 02_清理与校验.sh
```

## 第 4 节 · 清理清单（改了什么、为什么）

原包是第三方二次打包的，外壳里塞了几样**不能留**的东西。逐条记下来，免得下次又踩。

| # | 原包里的东西 | 处理 | 原因 |
|---|---|---|---|
| 1 | `双击修复损毁`（dmg 根目录） | **不复制、不执行** | 它执行 `sudo spctl --master-disable`，把整台机器的 Gatekeeper 关掉。为了开一个游戏而永久削弱系统防线，不能接受 |
| 2 | `load` 里的 `launchctl remove/load com.valvesoftware.steam.ipctool` | 删除 | 往用户的 launchd 里装卸服务＝改系统设置。本机没装 Steam，这两行纯属空转 |
| 3 | `load` 里的 `pkill ipcserver` | 改成 pid 文件精确回收 | 全局 pkill 会误杀同时运行的其它实例 |
| 4 | `steam_appid.txt` 放在 `Contents/MacOS/` | 挪到 `Contents/Config/` | `Contents/MacOS` 只该放可执行代码。混入纯文本后 `codesign` 直接报 `code object is not signed at all`，整个签名流程卡死 |
| 5 | 模拟器身份：`fengqs2` / `76561198441937569` | `Player` / `76561197960287930` | 原包带着打包者随机生成的账号名，换台机器没意义，也不该顶着别人的 ID |
| 6 | `CFBundleName = MilkGame` | `美女室友竟然` | 程序坞、菜单栏、Finder 都显示这个名字。Bundle ID 保持不变，存档路径不受影响 |
| 7 | dmg 里的 `常见问题.rtf`、`.background/`、`.DS_Store` | 不复制 | 广告站链接和窗口背景图，与游戏无关 |
| 8 | `Contents/Resources/load.orig.sh` | **保留**（只作对照） | 想确认「原版到底改了什么」时用，不要执行 |

清理后仍然保留的东西：`ipcserver`、`steamclient.dylib`、`reset`（42 KB，不再调用，删了怕影响模拟器的自检逻辑）、
`_CodeSignature`（重签后由系统重写）。

## 第 5 节 · 坑位清单（这次真踩到的）

1. **`ditto` 在受限环境里会整包变成临时文件**
   现象：复制「完成」后目录里全是 `.BC.T_xxxxxx`，目标文件名一个都没有；删残留时 31 GB 一起没了。
   解法：用 `cp -Rp`，或者复制完先 `find -name '.BC.T_*'` 数一下再决定删不删。

2. **`Contents/MacOS` 里不能有非可执行文件**
   现象：`codesign` 报 `code object is not signed at all`，`In subcomponent: …/steam_appid.txt`。
   解法：数据文件挪到 `Contents/Config`，启动器改成从那里读（`load_clean.sh` 已兼容两个位置）。

3. **内层重签很慢，别以为卡死了**
   33 GB 的 `resources.resource` 要整体哈希一遍：实测 **4 分 26 秒**（USB 固态）。
   所以 `02` 脚本只在「显示名真的变了」时才重签内层，平时只签外层（秒级）。
   要强制重签：`bash 02_清理与校验.sh "$APP" --force-inner`。

4. **外层 `CFBundleExecutable` 是个 shell 脚本**
   签名能通过，但**必须** `xattr -cr` 清干净；带着 `com.apple.provenance` 之类属性会 `SIGKILL`。

5. **挂载 dmg 一定加 `-nobrowse`**
   否则 Finder 会弹一个窗口，打断正在跑的自动化。

6. **游戏默认不写日志**
   `~/Library/Logs/Unity/` 是空的。要排查就手动带参数跑一条：

   ```sh
   APP="/Volumes/SSD/Game/MilkGame/美女室友竟然.app"
   export SteamAppId=3021100 SteamGameId=3021100 \
          STEAMEMU_SETTINGS_DIR="$APP/Contents/Config" \
          DYLD_LIBRARY_PATH="$APP/Contents/MacOS"
   cd "$APP/Contents/MacOS" && ./ipcserver & \
   "$APP/Contents/Game/MilkGame.app/Contents/MacOS/MilkGame" -logfile /tmp/fh_unity.log
   ```

   日志里这几条是**正常噪音**，不用管：
   - `Metal: Error creating pipeline state (UI/BlurNomal)` —— 一个 UI 模糊 shader 不兼容，游戏自动降级
   - `error messaging the mach port for IMKCFRunLoopWakeUpReliable` —— 输入法与后台进程通信的提示
   - `DOTWEEN ► SAFE MODE ► … 5 missing target or field errors` —— UI 补间找不到目标，引擎自己兜住了

7. **`ipcserver` 退出不干净会挡住下一次启动**
   `load_clean.sh` 用 `Contents/Config/ipcserver.pid` 精确回收；pid 文件残留就手动删。

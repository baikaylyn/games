# 塞尔达传说 Mac 原生版 —— 构建工作流

> 记录两台机器上实际跑通的构建过程：**王国之泪 1.4.3** 与 **旷野之息 1.9.0（含双 DLC）**。
> 重点是「从原始游戏文件到一个能双击运行的 .app」这条链路，以及启动器和着色器这两块最容易出问题的地方。
> 最后整理日期：2026-10-26。

---

## 0. 一句话说清它是什么

**不是模拟器。** Switch 和 Apple 芯片都是 ARM64，游戏的机器码几乎逐条原样跑在 Mac 上。项目补的是 Switch 原本提供的那三层：

| Switch 提供 | 项目对应实现 |
|---|---|
| 加载器 / 系统调用 | `runtime/loader.c` + `patch_nso.py` 预重写 |
| Horizon OS 服务（线程、文件、音频、输入…） | `runtime/*.c`（IPC 层 + 各服务） |
| 图形驱动 NVN | `third_party/d2r_gfx/gfx/nvn/` → 翻译成 Metal |

所以构建的本质是：**把游戏的三个可执行模块改写成 macOS 能跑的形态，把 RomFS 解出来，再把自己的 runtime 和它们打包进一个 .app。**

## 1. 前置条件

| 项 | 要求 |
|---|---|
| 硬件 | Apple Silicon（arm64）。实测 M4 / 16 GB |
| 系统 | macOS **15.0+**（`-mmacosx-version-min=15.0`，Metal 3 目标） |
| 编译 | Xcode Command Line Tools（`clang`、`codesign`、`hdiutil`、`lipo`） |
| Python | **3.14**（`../venv/bin/python`，Makefile 里通过 `PY=` 传入） |
| 库 | Homebrew 的 `opus`、`libvpx`（音频与 VP9 过场动画） |
| 外部工具 | `hactool`（固定 commit `1d64a83`）、SPIRV-Cross（构建时用 clang 现编） |
| 输入 | 本体 XCI/NSP、`--update` 更新包、`prod.keys`、共享字体（`--firmware` 或 `--shared-fonts`） |
| 磁盘 | 全新构建约 **25 GB**（带更新 **40 GB**）；App 与工作目录同卷时是 APFS 克隆，不额外占空间 |

**不支持**：NSZ/XCZ 格式的本体、合并包、个性化 ticket、TOTK 的 DLC。

## 2. 源码树：三个目录各是什么

```
_构建源码/
├── Source/                    原始上游：build_app.py、docs/、games/
├── Source-upstream-compat/    合并了上游 PR 的版本（含 docs/botw-v1.9.0-port.md）
└── Build/work/totk/           真正拿来编译的工作树
    ├── Makefile               所有编译目标都在这里
    ├── app/launcher.m         启动器（唯一一个 .m 界面文件）
    ├── runtime/               Horizon OS 层（loader、服务、补丁）
    ├── third_party/d2r_gfx/   图形层（NVN → Metal）
    └── build/                 编译产物、着色器种子、管线清单
```

**关键机制**：`build_app.py` 会先把 `Source/games/totk` 复制进工作目录（`prepare_work`），再在那里编译。所以：

- 改**代码** → 改 `Build/work/totk/` 下的文件，直接 `make` 就能验证
- 改**构建逻辑** → 改 `Source/build_app.py`
- 两边都改过之后要小心：下次跑 `build_app.py` 可能用 `Source/` 的内容覆盖工作树

## 3. 构建四步（`build_app.py`）

整个流程由 `main()` 串起来，日志写在 `<工作目录>/logs/`。

### 步骤 1 —— 代码（`step_code` / `step_code_botw`）

1. 按文件头判断容器类型：**HFS0**（XCI 卡带）或 **PFS0**（NSP）
2. **原地**读取 Program NCA，抽出 ExeFS（`main`、`sdk`、`subsdk0`、`rtld`、`main.npdm`）
3. 用 `patch_nso.py` 重写 macOS 不允许的部分：
   - 平台寄存器 `x18`、线程指针寄存器
   - 系统调用 `svc`
   - 计数器寄存器
   每一处都变成跳到 stub 的短跳转
4. 用 `assets/expected-v<版本>.json` 里的 pin **逐字节校验**重写结果 —— 版本不对就直接停（地址随版本怎么变，见第 4 节）
5. NSP 的 common ticket 在内存里解出 title key，`prod.keys` 提供 titlekek

> `main.npdm` 是唯一不要求逐字节相同的文件：它带有任天堂 ACID 签名，换一份正版 dump 签名也会不同。代码里用 PSS/SHA-256 验签，只要签名有效 + 代码模块哈希对得上就接受。

### 步骤 2 —— 数据（`step_data` / `step_data_botw`）

1. 解密 RomFS（TOTK 约 17 GB），**六层 IVFC 全部校验**通过
2. 抽共享字体（6 个 BFTTF）：来自 XCI 的系统更新分区、`--firmware` 目录，或 `--shared-fonts`
3. 生成 RomFS overlay（小的数据补丁）：高帧率下的快捷菜单截图时机、死亡重试、1440p 需要的堆大小
4. 有更新包时走 BKTR 合并（`hactool --sectionN`），最终镜像要匹配该版本的 SHA-256
5. BOTW 另有 `extract_dlc.py`，每个 DLC 包独立校验六层 IVFC，落到 `extracted/botw190/aoc/<index>`

### 步骤 3 —— 着色器（`step_shaders` / `step_shaders_botw`）

1. 用 clang 现编 **SPIRV-Cross**
2. 校验预编译翻译器 `totk_xlate` 的 SHA-256（.NET NativeAOT 产物，随源码附带，**构建和游玩都不需要 .NET**）
3. `prepare_shader_seed.py` 解压字典压缩包，扫描 `Shader/` 及 SDK/Bootup 包，解析支持的 BNSH/NVN 程序
4. 用**原生翻译器 + SPIRV-Cross** 生成默认绑定状态的 MSL、反射和依赖索引
5. 按运行时相同的 control + code SHA-256 去重；成功准备少于 8,000 个就**中止构建**
6. 产物落在 `build/shader-seed/`，附 `seed-manifest.json`（版本、翻译链、工具身份、每个文件的哈希）

> 这里**不打包任何 GPU 相关二进制**。Metal 库在目标机器上现生成，所以换机器不会拿到不兼容的缓存。

### 步骤 4 —— 二进制与打包（`step_binary` → `step_app`）

```
make runtime-<版本>-m3        # 编游戏 runtime
clang app/launcher.m          # 编启动器
step_app()                    # 组装 .app + 签名
lsregister -f <app>           # 刷新 LaunchServices
<app>/Contents/MacOS/<exe> --check    # 自检（版本 + 二进制存在）
step_warm_metal()             # 预热 Metal 库
```

两个 App 的目录名一样（`Contents/Resources/totk/` 是两个游戏共用的游戏目录，名字来自 `launcher.m`，不随游戏变），但**数据布局不同**，这是当前构建代码与旧产物的差别：

```
王国之泪 1.4.3（旧布局：RomFS 直接躺在 App 里）
Tears of the Kingdom M3.app/Contents/
├── Info.plist                     CFBundleShortVersionString = 1.4.3
├── PkgInfo
├── MacOS/TOTK                     启动器（约 100 KB）
├── Resources/totk/
│   ├── build/                     totk-native（runtime）、shader-seed/、shader-libs/、
│   │                              shader-service/totk_xlate、pso_manifest.tsv、pso_title.tsv
│   ├── extracted/
│   │   ├── firmware/
│   │   └── v143/
│   │       ├── romfs/romfs.bin        ← 真实文件，17,052,625,232 字节
│   │       ├── romfs/runtime-index.bin
│   │       ├── romfs-patches/
│   │       └── romfs-patches-out/
│   └── rewritten/                 main / sdk / subsdk0 三个 .patched.bin
└── _CodeSignature/
```

```
旷野之息 1.9.0（新布局：RomFS 抽成独立签名的 bundle）
Breath of the Wild.app/Contents/
├── Info.plist
├── PkgInfo
├── MacOS/BotW                    启动器
├── Helpers/
│   └── GameData-botw190.bundle/  ← 独立 App 形态的 bundle，内含 Contents/Resources/romfs.bin（14 GB）
├── Resources/totk/
│   ├── build/                     同上（runtime 换成 totk-native、种子换成 botw190）
│   ├── extracted/
│   │   ├── firmware/
│   │   └── botw190/
│   │       ├── romfs/romfs.bin         ← 符号链接：../../../../../Helpers/GameData-botw190.bundle/Contents/Resources/romfs.bin
│   │       ├── romfs/runtime-index.bin
│   │       └── aoc/<index>/            两个 DLC 各自的 romfs.bin + runtime-index.bin
│   ├── mouse.txt                  鼠标操作说明（只有旷野之息带）
│   └── rewritten/
└── _CodeSignature/
```

**为什么 RomFS 要单独做成 bundle**（`data_bundle()` / `place_data_bundle()`）：把 16 GB 直接塞进 App 里签名，每次打包都要重新哈希全部 16 GB（M4 上 88 秒，外接盘上 8 分钟）。做成独立 bundle 后，App 的封条只记录这个 bundle 的签名，镜像没变就直接复用（`build/data-bundles/GameData-<ver>.bundle.json` 记录 size / mtime / SHA-256 做命中判断）。游戏仍按老路径打开 `extracted/<ver>/romfs/romfs.bin`，只是那里变成了指向 bundle 的符号链接。

> **现状**：`step_app()` 对两个游戏都会调用 `place_data_bundle()`，所以**现在重新构建王国之泪会得到新布局**（多出 `Contents/Helpers`，`romfs.bin` 变成链接）。当前装着的王国之泪 App 是加入这个机制之前打的包，17 GB 镜像还在原位 —— 功能上没区别，只是每次重新打包仍要哈希全部镜像。要转换就得重跑一次 `build_app.py`，而它的工作目录 `extracted/` 已经删掉腾空间了，需要原始游戏文件重新提取。

**另外两个提速细节**：
- `keep_game_data()`：新 App 与已装 App 的数据包签名一致时，直接把旧的 bundle 挪进新 App（inode 和时间戳都不变），连克隆都省了
- 首次启动的 16 GB 校验结果被 `runtime/romfs.c` 按 size + mtime 记住，所以打包后第一次启动不会重新哈希

## 4. 地址依赖：为什么只有这几个版本能跑

runtime 干的事本质是「在游戏代码的**指定地址**上改一条指令」（把 30 fps 的下限改成 60、把 1920×1080 换成实际输出尺寸……）。而地址随版本变，所以整个项目把这份依赖显式收在三个地方：**宏表、指令守卫、字节 pin**。

### 4.1 机制：用 1.0.0 的地址当符号键

`runtime/game_version.h` 每个版本一个分支，写法是「1.0.0 的地址 → 该版本的真实地址」：

```c
#define GAME_ADDR_JOIN(x) GAME_ADDR_##x
#define GAME_ADDR(x) GAME_ADDR_JOIN(x)      /* 粘成宏名，编译期查表 */

#elif defined(TOTK_GAME_V143)
#define GAME_ADDR_0xe995c4 0xbdb48c   /* return address of nnMain's only call to nn::oe::SetFocusHandlingMode */
#define GAME_ADDR_0x2aa4fa0 0x2bb79f0 /* nn::swkbd::ShowKeyboard: main's PLT stub */
#define GAME_ADDR_0x453f648 0x398b348 /* nn::swkbd::ShowKeyboard: main's GOT slot */
```

代码里永远只写 `GAME_ADDR(0xe995c4)` —— 用 1.0.0 的地址当**符号键**，取到的是当前编译版本的值。共用代码（`loader.c`、`swkbd_host.c`，以及 TOTK 的 `world_survey.c`）都走这条路：

| 符号键（1.0.0 地址） | 王国之泪 1.4.3 | 旷野之息 1.9.0 | 用途 |
|---|---|---|---|
| `0xe995c4` | `0xbdb48c` | `0xc617e8` | nnMain 里唯一一次 `nn::oe::SetFocusHandlingMode` 调用的返回地址 |
| `0x2aa4fa0` | `0x2bb79f0` | `0x15a01a0` | `nn::swkbd::ShowKeyboard` 的 PLT stub |
| `0x453f648` | `0x398b348` | `0x1d78198` | 同上，GOT 槽 |

1.4.3 的表里有 7 项，旷野之息只有 3 项 —— 少的那几个是 TOTK 专属补丁点，在旷野之息里不存在。

**漏一项的后果是编译不过**（`GAME_ADDR_0x…` 变成未定义标识符），不会静默用到错的偏移。这是有意设计的：宁可编译失败，也不要运行时改错地方。

### 4.2 但 1.4.3 和旷野之息不用这张表

`game_patches_v143.c` 和 `game_patches_botw.c` 里 **0 处** `GAME_ADDR(` —— 它们本来就是为那个版本逐点找出来的，直接写死本版本的绝对偏移：

```c
/* game_patches_v143.c：60 fps 的 7 个站点，地址是 1.4.3 自己的 */
static const Patch fps60[] = {
    {0x2db204, 0x6b08015f, 0x7100055f},
    {0x2db208, 0x1a89b10a, 0x1a9fa52a},
    …
};
```

所以三份补丁文件按版本分开：1.0.0 / 1.1.2 用 `game_patches.c`（走宏表），1.4.3 用 `game_patches_v143.c`，旷野之息用 `game_patches_botw.c`（`GAME_BOTW` 同时把用 TOTK 地址的共享代码编译掉）。

### 4.3 三道防线

**① 编译期 —— 宏表**。版本选错，地址就是错的；这一层只能保证「表里有的都对」，防不了表本身写错。

**② 运行期 —— 指令守卫**（真正的保险）。每个补丁点都带「原指令字」，写之前先比对：

```c
typedef struct { uint64_t offset; uint32_t original, replacement; const char *what; } GamePatch;
…
if (word != p->original) { fprintf(stderr, "[totk] …found %08x, expected %08x (%s)\n", …); return; }
```

不符就**跳过并报错，绝不盲写**。关键路径上是硬失败：

```c
runtime_fail("real-time frame-step requires matching game-version original instructions");
```

`loader.c` 还额外做一条地址断言，确认这个回调确实是从原版 nnMain 进来的：

```c
need(caller == (uintptr_t)modules[0].base + GAME_ADDR(0xe995c4), "checkpoint not reached from original nnMain");
```

**③ 打包期 —— 字节 pin**。`assets/expected-v<版本>.json` 把重写结果的全部哈希钉死，任何一步地址算错都过不了：

```
exefs_sha256{main, main.npdm, rtld, sdk, subsdk0}     原始模块
rewritten_sha256{main.patched.bin, sdk.patched.bin, subsdk0.patched.bin}   重写后
romfs{size, sha256}  +  shared_fonts_sha256{6 个字体}
```

### 4.4 两个不是「代码地址」的依赖

- `GAME_OUTPUT_CALL_WORD`：同一个 `bl` 指令在不同版本里编码不同（1.0.0 是 `0x94000082`，1.1.2 是 `0x94000083`），因为调用目标的相对距离变了。它作为守卫字进了版本表；1.4.3 那块没有这一项，因为 1.4.3 编译的是 `game_patches_v143.c`，根本不用 `game_patches.c`。
- `GAME_ACTOR_*`：结构体字段偏移（1.4.3 是 `name 0x218` / `pos 0x2b4` / `rot 0x2c0`，1.0.0 是 `0x210/0x2ac/0x2b8`），给世界测量（`world_survey.c`）用。版本一变字段就挪，同样是地址依赖。旷野之息走的是另一套指针链（`[[main+0x2d37af0]+0xf0]+0xd28]+0x5e0`），不用这两个宏。

### 4.5 加一个新版本要做什么

1. `scripts/map_version_sites.py --from v112 --to <版本> --header` —— 拿已知版本里每个站点周围的指令窗口去新版本里找唯一匹配（PC 相对字段、ADRP 后的页偏移全部掩码；数据站点通过寻址它的代码找；导入函数的 GOT/PLT 通过 `JUMP_SLOT` 重定位按符号名找），直接吐出 `game_version.h` 的新分支。它自带自检：`--from v0 --to v112` 必须复现 1.1.2 那一块（实测 32/32）。
2. **注意它打印的是两个版本的原始指令字** —— 站点搬了家但指令字变了的话，需要的是新的 `original` 期望值，而不只是新偏移。这一步搞错，运行时会报「found …, expected …」然后跳过补丁。
3. 补 `assets/expected-v<版本>.json`（exefs / rewritten / romfs / shared_fonts 四组哈希）。
4. `scripts/game_version_test.py --version <版本>` 做地址一致性自检。
5. 新版本若少了某些补丁点（旷野之息就没有 TOTK 的 60 fps 控制器站点），单独写一份 `game_patches_<版本>.c`，**不要**往共用表里塞条件编译。

## 5. 两个游戏的差异对照

同一套 runtime、同一套图形层，靠**编译宏**分家：

| 项 | 王国之泪 1.4.3 | 旷野之息 1.9.0 |
|---|---|---|
| 编译宏 | `TOTK_GAME_V143=1` | `GAME_BOTW=1` `GAME_BOTW190=1` |
| make 目标 | `runtime-v143-m3` | `runtime-botw190-m3` |
| 工作目录 | `TOTK_build` | `BotW_build` |
| 输出 App | `Tears of the Kingdom M3.app` | `Breath of the Wild.app` |
| 可执行名 | `TOTK` | `BotW` |
| 数据目录 | `MacNativeGames/TOTK` | `MacNativeGames/BOTW` |
| 日志 | `totk.log` | `botw.log` |
| 着色链 | `totk-native-v4-unverified` | `totk-native-v7-unverified` |
| 种子着色器数 | 8,290 | 11,947 |
| 图形对象目录 | `build/gfx-m3` | `build/gfx-botw190-m3` |
| 额外输入 | `--update` 1.4.3 | `--update` 1.9.0 + 两个 `--dlc` |
| 游戏补丁文件 | `game_patches.c` / `game_patches_v143.c` | `game_patches_botw.c` |
| RomFS 规模 | 约 17 GB | 15,132,662,100 字节 / 41,062 文件 |

`GAME_BOTW` 是总开关，`GAME_BOTW160` / `GAME_BOTW190` 再分具体版本。同一个工作树里两套代码靠 `#ifdef` 共存，**改一处一定要想清楚落在哪个分支**。

## 6. 实际编译命令

### 游戏 runtime（以王国之泪为例）

```sh
cd Build/work/totk
make -j$(sysctl -n hw.ncpu) runtime-v143-m3
```

旷野之息：

```sh
make -j$(sysctl -n hw.ncpu) runtime-botw190-m3
```

`PY` 默认是 `.venv/bin/python`（符号链接到 `Build/work/venv`，由 `prepare_work` 建好并装好 `requirements.txt`），一般不用传。注意 **Metal 3 版本必须带 `-m3` 后缀**：不带的是 Metal 4 目标，在 macOS 15 上跑不起来；`build_app.py` 是靠环境变量 `TOTK_M3=1` 决定加不加这个后缀的。

两条规则展开后都是同一条 clang 命令行（TOTK 版，`runtime-v143-m3`）：

```

  -mmacosx-version-min=15.0 -DDM_NVN_M3=1 \

  -DTOTK_GAME_V143=1 -Ibuild/v143 -Ibuild \

  runtime/loader.c runtime/game_patches_v143.c runtime/world_survey.c runtime/game_slot.c \
  runtime/services.c runtime/romfs.c runtime/threads.c runtime/gate.S runtime/hle_stack.S \
  runtime/hle_stack.c runtime/thread_enter.S runtime/gfx_bridge.c runtime/frontend.m \
  …（共 36 个源文件）… \
  $(GFX_OBJECTS_M3) \
  /opt/homebrew/opt/opus/lib/libopus.a /opt/homebrew/opt/libvpx/lib/libvpx.a \
  -framework Metal -framework MetalFX -framework Foundation -framework QuartzCore \
  -framework ImageIO -framework CoreGraphics -framework CoreText \
  -framework UniformTypeIdentifiers -fobjc-arc -framework Cocoa -framework CoreVideo \
  -framework CoreFoundation -framework AudioToolbox -framework GameController \
  -framework CoreHaptics -framework IOKit \
  -o build/totk-native-v143-m3
```

旷野之息那条只是把宏换成 `-DGAME_BOTW=1 -DGAME_BOTW190=1`、`-Ibuild/botw190`、`game_patches_v143.c` → `game_patches_botw.c`，并多两个源文件 `aoc_romfs.c`（DLC 的 RomFS 挂载）和 `settings_service.c`，共 **38 个**；图形对象目录也从 `build/gfx-m3` 换成 `build/gfx-botw190-m3`。

> 图形层是**先编成 .o 再链接**的（`build/gfx-m3/%.o: % $(GFX_HEADERS)`），所以 `GFX_OBJECTS_M3` 才是耗时大头。

### 启动器（改 `app/launcher.m` 后单独重编）

`build_app.py` 里的原版（两个游戏都输出到同一个文件名，靠 `defines` 区分）：

```sh
# 王国之泪：defines = -DTOTK_GAME_V143=1
# 旷野之息：defines = -DGAME_BOTW190=1
xcrun clang -fobjc-arc -O2 -Wall \
  -Ithird_party/d2r_gfx/gfx/nvn -Iruntime \
  -DTOTK_GAME_V143=1 \
  app/launcher.m -framework AppKit -framework GameController \
  -o build/app-launcher
```

手动重编、想两个游戏各留一份时，我在工作目录里用的是这两个文件名（`build_app.py` 不会覆盖它们）：

```sh
xcrun clang -fobjc-arc -O2 -Wall -Ithird_party/d2r_gfx/gfx/nvn -Iruntime \
  -DTOTK_GAME_V143=1 app/launcher.m \
  -framework AppKit -framework GameController -o build/app-launcher-totk

xcrun clang -fobjc-arc -O2 -Wall -Ithird_party/d2r_gfx/gfx/nvn -Iruntime \
  -DGAME_BOTW190=1 app/launcher.m \
  -framework AppKit -framework GameController -o build/app-launcher-botw
```

> 旷野之息只要给 `-DGAME_BOTW190=1` 就够 —— `runtime/game_version.h` 会在 `GAME_BOTW190` 存在时自己定义 `GAME_BOTW`，启动器的三个字符串（文件夹、日志名、标题）就都跟着切过去了。

### 装回去

```sh
cp build/app-launcher-totk "…/Tears of the Kingdom M3.app/Contents/MacOS/TOTK"
cp build/app-launcher-botw "…/Breath of the Wild.app/Contents/MacOS/BotW"
codesign --force --deep --sign - "…/Tears of the Kingdom M3.app"
codesign --force --deep --sign - "…/Breath of the Wild.app"
codesign --verify --strict "…/Tears of the Kingdom M3.app"
```

> ⚠️ **改任何二进制都必须重签**，否则 App 起不来。
> `codesign --deep` 对 16 GB 的 App 要约 60 秒，前台跑容易被超时打断 —— 放后台。
> 只换了启动器、数据包没动的话，也可以只重签 App 本体（`codesign --force --sign - <app>`，不加 `--deep`），几秒完成 —— 前提是 `Contents/Helpers` 里那份 bundle 自己的签名没被碰过。

### 改完代码后的最短验证路径

| 改了什么 | 要跑什么 | 大概耗时 |
|---|---|---|
| `runtime/*.c`、`runtime/*.m` | `make runtime-<版本>-m3` → 拷 `build/totk-native-<版本>-m3` 到 App 的 `Resources/totk/build/totk-native` → 重签 | 2–4 分钟 |
| `app/launcher.m` | 上面那条单编命令 → 拷进 `Contents/MacOS/` → 重签 | 约 5 秒 + 重签 |
| `third_party/d2r_gfx/gfx/nvn/` 下的**头文件** | 先 `touch nvn_mtl.m totk_shader_rt.m`，再 `make runtime-<版本>-m3` | 5–10 分钟（图形层重编） |
| `build_app.py` / `Makefile` | 直接跑 `build_app.py` 完整流程，让它自己打包 | 11 分钟起 |
| 只改启动器界面文字 | 同上单编 → 用 `strings` 或 Python 查 UTF-16LE 确认（Objective-C 字面量在二进制里是 UTF-16） | 秒级 |

**验证不用开游戏**：`<app>/Contents/MacOS/<exe> --check` 只校验版本和二进制存在，几秒返回。真要确认画面，看日志里的「出图节拍」和「shader-seed」两行就够（见第 12 节）。

## 7. 启动器（`app/launcher.m`）

一个 600 多行的 AppKit 文件，职责有三件：**选配置 → 设环境变量 → exec 游戏**。

### 7.1 生命周期

```
main()
 ├─ 解析路径：data / logs / slot / cache / profile
 ├─ --check          → 只校验版本和二进制，供打包流程自检
 ├─ 已有游戏在跑？    → 只把窗口带到前台，不重复启动
 ├─ 建窗口（TOTKLauncher）
 ├─ TOTK_LAUNCHER_AUTO=1 或 --play → 跳过窗口直接开始
 └─ startGame:  → 写 launcher-settings.json → setenv 一堆 → execv
```

### 7.2 窗口里的设置项

| 分组 | 选项 | 落到哪个环境变量 |
|---|---|---|
| 路径 | 存档 profile、Mod 目录 | `TOTK_PROFILE_DIR`、`TOTK_ROMFS_PATCHES` |
| 浮层 | FPS / 着色器 / 系统负载 | `TOTK_FPS_OVERLAY`、`TOTK_SHADER_OVERLAY`、`TOTK_LOAD_OVERLAY` |
| 性能 | 性能模式（1x 画布） | `TOTK_DRAWABLE_SCALE=0.5` |
| 性能 | 关闭 MetalFX 输出超分 | `TOTK_MFX_OUTPUT=0` |
| 性能 | MetalFX 空间超分 | `TOTK_MFX_UPSCALE` |
| 性能 | 跳过首次着色器预热 | `DM_PSO_MANIFEST=off` |
| 性能 | **锁定 60 帧** | `DM_PRESENT_HZ=60` |
| 显示 | 全屏 / 输出分辨率 / 窗口尺寸 / 比例 / 填充 | `TOTK_FULLSCREEN`（不开则 `TOTK_WINDOW_MAX=1` 无边框）、`TOTK_OUTPUT_RES`、`TOTK_WINDOW_SIZE`、`TOTK_ASPECT_RATIO`、`TOTK_PICTURE_FILL` |
| 手柄 | HD 震动 / 六轴体感 / 交换 ABXY | `TOTK_RUMBLE`、`TOTK_GYRO`、`TOTK_GAMEPAD_SWAP_ABXY` |

两个默认值值得记住：**「跳过首次着色器预热」默认关**（少一次预热就会出黑块，不值得），**「锁定 60 帧」默认开**（两个游戏都不需要超过 60 帧）。设置存在 `launcher-settings.json`，缺键时用这两个默认值。

### 7.3 启动器固定注入的变量

```c
TOTK_PROFILE_DIR      存档目录
TOTK_SHADER_CACHE     shader-cache/rt-<DMSH_CHAIN>
TOTK_GAME_SLOT_DIR    单实例锁
TOTK_ROMFS_PROOF_DIR  RomFS 校验记录（App 内保持只读）
TOTK_SHARED_FONTS     extracted/firmware/shared-fonts
TOTK_GPU_ALLOW_SUBMIT / WIDEN / BLOCKRT / MIDCLEAR
TOTK_GPU_BUDGET_MB    5000   ← 显存预算，超了 App 会停游戏
TOTK_SLOT_OWNER=user  TOTK_SLOT_PURPOSE=player
TOTK_INPUT_FILE       <数据目录>/input.txt（运行时命令通道）
unsetenv("TOTK_AUTOLOAD")    ← 明确清掉，保证从标题画面开始，和主机一致
```

另外每次启动都会做日志轮转：`<log>.log` → `<log>.previous.log`，再新建一个空的当前日志（所以「上一轮」总是 `.previous.log`）。

### 7.4 两个容易踩的设计点

**① 数据目录与日志名不能硬编码成 TOTK。**
启动器是同一份源码给两个游戏编译的，早期把标题、`MacNativeGames/TOTK`、`totk.log` 写死了，旷野之息那份只能在链接后打等长字节补丁改字符串 —— 一重建就退回 TOTK。现在改成按宏分支：

```c
#if defined(GAME_BOTW)
#define LAUNCHER_FOLDER "BOTW"
#define LAUNCHER_LOG    "botw"
#define LAUNCHER_TITLE  "Breath of the Wild Mac"
#else
#define LAUNCHER_FOLDER "TOTK"
#define LAUNCHER_LOG    "totk"
#define LAUNCHER_TITLE  "Tears of the Kingdom Mac"
#endif
```

**② `launcher-settings.json` 里的路径要能跨机器。**
`profile` 原来存绝对路径 `/Users/<某人>/…`，换台电脑用户名不同，`make_dir` 建不出来 → 启动器直接弹「无法创建 profile 文件夹」，游戏根本起不来。两条修正：

- **读**：保存的路径不在本机 home 下且不存在 → 丢弃，回落到本机默认目录（外接盘上真实存在的路径仍保留）
- **写**：等于默认目录时存**空字符串**

配置文件因此变成机器无关的。（可移植性的完整说明见第 11 节）

## 8. 着色器：三条路径

这是整个项目最复杂的部分，也是「新场景卡顿 / 黑块」的根源。

### 8.1 三种来源

| 来源 | 时机 | 产物 | 可移植性 |
|---|---|---|---|
| **种子导入** | 首次启动，第一帧之前 | `<data>/shader-cache/rt-<chain>/` | 可移植（`.metal` + `.json` 是文本） |
| **运行时翻译** | 遇到新变体时 | 同上，按需追加 | 同左 |
| **管线预测** | 预热阶段 | `pipelines/` | **不可移植**（GPU + 系统版本绑定的机器码） |

### 8.2 翻译链（`DMSH_CHAIN`）

一个字符串同时决定三件事：

1. `seed-manifest.json` 的 `chain` 字段（打包时写死）
2. 缓存目录名 `rt-<chain>`
3. 启动时的种子身份校验

**三者必须一致，否则启动直接报 `Startup shader seed identity is invalid`。**

```
王国之泪 1.4.3 → totk-native-v4-unverified
旷野之息 1.9.0 → totk-native-v7-unverified
```

`dmsh_chain.h` 里按 `GAME_BOTW` 分支。启动器自己也 include 这个头文件来算缓存目录 —— 所以**改链名必须连启动器一起重编**。

### 8.3 预热与「跳过预热」

启动器那个复选框的真实标签是：

> **「跳过首次着色器预热（更快；可能编译黑块/卡顿）」**

勾上 → `DM_PSO_MANIFEST=off` → 不预热，着色器现用现编。表现就是：菜单里的物品图标变成品红噪点、人物变纯黑剪影、进新区域出现方格化。**取消勾选**走完整预热即可，代价是首次启动多等几分钟。

### 8.4 帧率节拍

`hle_nvn.c` 的 `present_cfg()` 决定出图节奏：

```c
g_hz = e ? atoi(e) : (realtime && scr > 0 ? scr : 60);   // e = DM_PRESENT_HZ
g_uncapped = !e && realtime && … && g_hz < 120;          // 显式给了就不限帧
```

- 不给 `DM_PRESENT_HZ` → 跟随显示器；若显示器 < 120 Hz，进「不限帧」模式，上限 `TOTK_UNCAPPED_HZ`（默认 120）
- 给 `DM_PRESENT_HZ=60` → 固定 60 Hz 节拍，同时关掉不限帧

> 60 Hz 屏幕上，游戏其实一直在跑 120 帧再合并显示，锁 60 能把 GPU 负载砍一半。

## 9. Metal 4 → Metal 3 兼容层

上游图形层是按 **Metal 4** 写的，而 macOS 15 只有 Metal 3。`m3_compat.h/.m` 用 `DM_NVN_M3=1` 切进来，四个设计取舍：

1. **不包装编码器** —— 那要改 391 个站点的类型和所有权。改用宏把 MTL4 类型名映射到 Metal 3 对应物
2. **参数表做成真实对象** —— 自己记住「挂在哪个编码器、哪个阶段」，绑定时直接落到下层编码器
3. **屏障变空操作** —— Metal 3 靠自动 hazard tracking
4. **时间戳 / 提交回调 / 分配器** —— 各给一个薄壳

> 引入顺序有硬要求：**必须在所有 Apple 头文件之后**。这些宏会改写 MTL4 类型名，若在解析 `Metal.framework` 时生效，会把 Metal 自己的 `@interface` 一起改名，导致重复定义。

## 10. 实战踩过的坑

按遇到顺序，都是实际修过的：

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | TOTK 启动报 `seed identity is invalid` | 把 `DMSH_CHAIN` 全局改成 v7，但 TOTK 的 seed 是 v4 | 按 `GAME_BOTW` 分分支 |
| 2 | TOTK 目标链接失败：`_runtime_diag_watch_trap` 未定义 | 工作树缺该函数实现，BOTW 因 `#ifdef` 跳过了调用点所以没暴露 | 加 `__attribute__((weak))` 的**弱定义**（加在声明上无效，必须给定义） |
| 3 | 改了 `dmsh_chain.h`，make 说 "Nothing to be done" | `GFX_HEADERS` 在第 151 行才赋值，而规则在第 15 行定义 → 头文件不进依赖 | `touch nvn_mtl.m totk_shader_rt.m` 强制重编 |
| 4 | 稀疏 MRT 空洞填充 → 立刻 SIGSEGV | 管线在空洞处声明的格式是 0，绑真实纹理对不上；即使对齐 textureType / arrayLength / sampleCount 仍崩 | 保持默认关（`TOTK_SPARSE_MRT_FILL`），M3 上不做填充 |
| 5 | 旷野之息人物全黑 | G-buffer 把同一张贴图挂到两个颜色槽，Switch ROP 只写掩码通道；Apple TBDR 每个附件独立 tile、pass 结束整块写回，后写回的空槽覆盖了 albedo | `rt_dup_of()` 识别重复颜色槽并跳过（`TOTK_RT_DUP_SKIP=0` 可关闭做 A/B） |
| 6 | 菜单图标品红、人物黑剪影 | 启动器勾了「跳过首次着色器预热」 | 取消勾选，走完整预热 |
| 7 | 重建旷野之息启动器后标题变回 "Tears of the Kingdom" | 字符串硬编码 + 链接后字节补丁 | 改成 `LAUNCHER_TITLE` 等宏 |
| 8 | 换机器后启动器弹「无法创建 profile 文件夹」 | `launcher-settings.json` 存了绝对路径 | 读时校验、写时存空串 |
| 9 | 拷到外接盘后 App 报签名损坏 | 用 `cp` 而非 `ditto` | 一律 `ditto`（保留签名、扩展属性、符号链接） |

## 11. 路径依赖与可移植性：拷到别的 Mac 上还能不能跑

**结论：能。** App 是自包含的 —— 16–17 GB 的游戏数据在 App 里，运行时所有路径都在启动那一刻现算。除了调试信息（`-g` 的 DWARF，运行时不读）之外，唯一一处真正被运行时读到的构建机绝对路径，已经被启动器覆盖掉了（11.4）。

### 11.1 四条前提

| 项 | 要求 | 为什么 |
|---|---|---|
| CPU | Apple Silicon（arm64） | 二进制是 `Non-fat file … architecture: arm64`，没有 x86_64 切片，Rosetta 也转不了 |
| 系统 | macOS **15.0+** | `LSMinimumSystemVersion = 15.0`（图形层是按 Metal 3 编的） |
| 目标卷 | **必须支持符号链接**（APFS / HFS+） | 旷野之息的 `romfs.bin` 是指向 `Contents/Helpers` 的符号链接；exFAT / FAT32 存不了链接，App 会坏 |
| 拷贝方式 | `ditto`，不要 `cp -R` | 保留符号链接、扩展属性、签名（踩过：`cp` 拷完报「签名损坏」） |

从网盘/网络下来的还要去隔离，否则 Gatekeeper 直接拦：

```sh
xattr -dr com.apple.quarantine "<app>"
```

### 11.2 运行时的路径是算出来的，不是记下来的

`app/launcher.m` 的 `main()` 定路径，`startGame:` 里把它们交给游戏：

```objc
NSString *root = [NSBundle.mainBundle.resourcePath stringByAppendingPathComponent:@"totk"];
NSString *home = NSHomeDirectory();
NSString *data = [home stringByAppendingPathComponent:@"Library/Application Support/MacNativeGames/" LAUNCHER_FOLDER];
NSString *logs = [home stringByAppendingPathComponent:@"Library/Logs/MacNativeGames"];
…
chdir(self.root.fileSystemRepresentation);          // 游戏按相对路径找自己的数据
setenv("TOTK_SHARED_FONTS", "extracted/firmware/shared-fonts", 1);   // 相对路径
```

两个关键点：

- `chdir(root)` 之后，游戏内部所有 `extracted/…`、`build/…` 都**相对 App** 解析 → App 搬到哪都成立
- 存档、缓存、日志、单实例锁全在 `~/Library` 下，按**当前用户**现算 → 换了用户名也不会指向别人的 home

实测：两个启动器二进制里 `strings | grep /Users/` 都是 **0 条**。

### 11.3 跟着「机器」而不是「App」走的三样东西

1. **`launcher-settings.json` 在数据目录**，不在 App 里 → 拷 App 不带设置，新机器从默认值开始。**但如果你把数据目录（`~/Library/Application Support/MacNativeGames/<游戏>`）一起拷过去，设置也会跟过去** —— 里面的 `profile` 已经是机器无关的空串，所以是安全的
2. **`profile`**：已改成机器无关 —— 等于默认目录时存**空串**；读的时候如果路径不在本机 home 下且不存在，就丢弃回落到默认（外接盘上真实存在的路径仍然保留）
3. **`mod` 路径没有同样的校验**：设过 Mod 目录的话，换机器后那一栏还留着旧路径。目录不存在时只是没有 overlay（日志打 `RomFS overlay: none`），不会崩，但建议清空

### 11.4 唯一一处编进二进制的绝对路径（已被启动器覆盖）

`build/shared_fonts_config.h` 由 `prepare_shared_fonts.py` 生成，里面是**构建机**的字体路径 + 大小 + SHA-256：

```c
{"/Users/<构建机>/…/extracted/firmware/shared-fonts/0-standard.bfttf", 2053636ULL, 2053628ULL, "823913c9…"}
```

`runtime/shared_font.c` 的取法：

```c
const char *dir = getenv("TOTK_SHARED_FONTS"), *base = strrchr(rows[i].path, '/');
FILE *f = fopen(dir ? path : rows[i].path, "rb");   // dir 有值 → 只取文件名，拼到 dir 下
```

- 启动器每次都设 `TOTK_SHARED_FONTS=extracted/firmware/shared-fonts` → **只用文件名**，路径跟着 App 走
- 绕过启动器直接跑 `Contents/Resources/totk/build/totk-native` → 走 fallback 绝对路径 → 换机器后 `runtime_fail("open shared font")`

**所以「必须从启动器进游戏」不只是操作习惯。** 两条路径都对字体做 SHA-256 校验，换机器不会拿到错的文件。

### 11.5 新机器第一次启动会重做什么

| 项 | 原因 | 代价 |
|---|---|---|
| RomFS 全量 SHA-256 | 校验记录 `.romfs-verified-v1` 在数据目录里，新机器没有；而且记录里含 ctime / birth time，拷贝后必然不匹配 | 16 GB 约 20 秒（M4） |
| 启动着色器预热（Metal 库） | Metal 缓存是每机每系统版本的（`~/Library/Caches/com.apple.metal`），不随 App 走 | 几分钟，一次性 |
| 首次扫描整个 App | 换了卷/新机器，Gatekeeper / XProtect 要重扫一遍 | 16 GB 几分钟，一次性 |
| 种子导入 | 从 App 内的 `shader-seed/` 导入到数据目录 | 一次性（8,290 / 11,947 个） |

着色缓存里的 `pipelines/` 是 GPU + 系统绑定的机器码，拷过去没用；`.metal` + `.json` 是文本，可移植 —— 所以**整个 `shader-cache` 目录可以直接拷到新机器**（同一个 chain 名、同一个游戏版本才行）。

### 11.6 签名这一层

两个 App 都是 `Signature=adhoc`（本机自签，`TeamIdentifier=not set`）：

- 不需要开发者证书，也不需要公证
- 拷到别的 Mac 上仍然有效，而且**只读的 App 放在外接盘上也能直接跑**（签名不依赖路径）
- 但**动过 App 里任何文件就必须重签**（`codesign --force --sign - <app>`，数据包没动就别加 `--deep`）

### 11.7 拷到新机器前的核对清单

```sh
lipo -info "<app>/Contents/MacOS/TOTK"                                                  # → arm64
/usr/libexec/PlistBuddy -c "Print :LSMinimumSystemVersion" "<app>/Contents/Info.plist"  # → 15.0
codesign --verify --strict "<app>" && echo 签名通过
ditto "<app>" "/Volumes/<盘>/<app>"        # 跨卷必须 ditto；目标卷不能是 exFAT
"<app>/Contents/MacOS/TOTK" --check        # → ok: game version 1.4.3（不用开游戏）
```

## 12. 验收清单

构建完成后按顺序过一遍：

```sh
# 1. 版本自检（打包流程自己也会跑）
"<app>/Contents/MacOS/TOTK" --check      # → ok: game version 1.4.3
"<app>/Contents/MacOS/BotW" --check      # → ok: game version 1.9.0

# 2. 签名
codesign --verify --strict "<app>"       # 无输出 = 通过
codesign -dv "<app>" | grep -E "Identifier|Signature"
#   → Identifier=org.macnativegames.totk / Signature=adhoc

# 3. 种子身份（进游戏后看日志）
grep "shader-seed" ~/Library/Logs/MacNativeGames/totk.log
#   → [totk-gfx] [shader-seed] 发现随 App 准备的着色器 8290 个，导入 0 个文件；首次启动即可预热

# 4. 出图节拍
grep "出图节拍" ~/Library/Logs/MacNativeGames/totk.log
#   锁 60 帧应为：出图节拍 60 Hz，间隔模式 game（原版语义）（游戏设的出图间隔 1；显式指定）

# 5. 存档是否被正确读写
ls ~/Library/Application\ Support/MacNativeGames/TOTK/profile/save/209ac…/
```

## 13. 时间参考（M4 / 16 GB）

| 阶段 | 耗时 |
|---|---|
| 首次全新构建（含解包 17 GB RomFS） | 约 1.5–2 小时 |

| 单编 runtime（`make runtime-*-m3`） | 2–4 分钟 |
| 单编启动器 | 约 5 秒 |

| 首次启动：导入种子 + 预热 8,290 个着色器 | 约 10 分钟（一次性） |
| 之后每次启动 | 几秒 |

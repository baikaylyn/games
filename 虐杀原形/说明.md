## 第 0 节 · 情况判别表（先看这里，九成不用重建）

| 症状 | 真正原因 | 怎么办 | 耗时 |
|---|---|---|---|
| 双击没反应，面板都不出来 | 上一个启动器实例还活着；或 LaunchServices 把它记成"常驻运行" | `pkill -9 -f 'MacOS/Prototype'` 再双击 | 10 秒 |
| 面板出来了，点「开始游戏」什么都没发生 | 上一次被强杀，`winedevice.exe` / `services.exe` 还占着 prefix | 启动器会先自己清一遍；没清掉就 `pkill -9 -f 'Resources/Wine'` 再点 | 15 秒 |
| 启动 3 秒左右直接退出，日志里 `Exception c0000005 in system thread` | **MoltenVK 没禁掉**（见第 6 节第 21 条） | 确认 `Wine/lib/libMoltenVK.dylib` 已改名成 `.disabled`；重建时 `build_prototype.py` 会自动做 | 1 分钟 |
| 卡在一个黑窗口里，既不退出也不出画面 | 启动崩溃（Rosetta 模式切换，见第 6 节第 8 条）或**静默卡死** | 正常情况下补丁已根治；**别动**，看门狗每 20~25 秒自己重来一次（最多 5 次） | 最长 2 分钟 |
| 日志里出现 `page fault ... at address 7BF21239`（或 `7BF21135`） | `wow64cpu.dll` 的补丁丢了（换过 / 重装过 Wine） | 重跑 `_build/wow64cpu_rosetta_patch.py`，然后 `codesign --force --deep -s - /Volumes/SSD/Game/Prototype/Prototype.app` | 1 分钟 |
| 点了开始游戏马上就回「就绪」，日志一行没加 | 渲染后端选着 DXVK，但 `Game/` 里没有 `d3d9.dll` | 现在会自动切回 wined3d；确认面板「渲染后端」是 wined3d | 5 秒 |
| 连续 5 次都没能启动 | 运气太差，或环境真坏了（prefix 半损） | 先再点一次「开始游戏」（会重新给 5 次机会）；还是不行就「重置环境」，约 1 分钟 | 30 秒 / 1 分钟 |
| 白窗口，几十秒后自己退出 | App 路径里有中文 | 移到纯英文路径（`/Volumes/SSD/Game/Prototype/` 就是对的） | 1 分钟 |
| 跑一两分钟后崩（`RtlpWaitForCriticalSection`） | CPU 核心设成了「全部核心」 | 改回 4 核（游戏自带的 `Restrict Cores.bat` 也是 4 核） | 10 秒 |
| 主菜单只有十几帧 | wined3d 的翻译开销，不是配置错 | 见第 9 节：这一项基本无解，别在上面耗时间 | — |
| 片头 400 多帧、主菜单十几帧 | 同上，同一个进程 | 正常现象，不是坏了 | — |
| 存档没了 | — | 见第 7 节（面板有「备份存档」按钮） | — |
| 弹「想要访问"文稿"文件夹」 | macOS 首次访问 `~/Documents` | 点**允许**（一次性） | 1 秒 |
| App 整个没了 | — | 从 `Prototype.rar` 重打包，见第 3 节 | 20 分钟 |

**结论：只有「App 整个没了」才需要走第 3 节。其余都是配置或残留进程问题。**


**关键技术栈**：

```
Windows 版 prototypef.exe（PE32 / i386 / DirectX 9，2009 年的引擎）
  → Wine 11.18 (Staging)，x86_64 Mach-O，整个跑在 Rosetta 2 翻译层下
      └ 游戏是 32 位 PE，走 Wine 的新 WoW64（lib/wine/i386-windows 里的 PE dll + 64 位 unix 侧）
  → wined3d（D3D9 → OpenGL 4.1 core，Apple 的 GL 驱动）
  → Metal → Apple M4 GPU
```

> **为什么不能像塞尔达那样原生跑**：王国之泪是 ARM64 + NVN，机器码能原样执行，补三层 API 就够。
> 虐杀原形是 x86-32 + Win32 + D3D9，**机器码一条都不能直接跑**，只能整条链翻译。
> 这三层（Rosetta 2 / Wine / wined3d）没有一层是能自己写的，能做的是把它们打包成一个自包含 App。

**版本坐标（重建后必须对得上）**：

## 第 3 节 · 从零重建（App 整个没了才需要）

### 3.1 准备

- 空闲空间 **≥ 20 GB**（8 GB 素材 + 8.6 GB App + prefix）
- 路径必须**纯英文**。中文路径会被 Wine 转成 `????`，引擎初始化直接失败（白窗口后静默退出）
- 时间：解压 8 GB 约 5–8 分钟，构建 + 签名约 2 分钟，首次启动建 prefix 约 1 分钟

### 3.2 解素材

`Prototype.rar` 里是两个目录：`Prototype/`（游戏本体）和 `_CommonRedist/`（运行库，Wine 下不需要）。

```sh
mkdir -p ~/Games/Prototype/_src
cd /tmp && bsdtar -xf "/Volumes/SSD/Game/Prototype.rar" Prototype
mv Prototype ~/Games/Prototype/_src/Game
```

Wine 运行时不在 rar 里，要单独取：**Gcenx 的 wine-staging 11.18 osx64 包**，解开后目录里应该有 `bin/ lib/ share/`：

```sh
mv wine-staging-11.18-osx64 ~/Games/Prototype/_src/Wine
~/Games/Prototype/_src/Wine/bin/wine --version    # 要打印 wine-11.18 (Staging)
```

### 3.3 构建

```sh
cd "/Volumes/SSD/Game/游戏构建/虐杀原形/_build"
python3 build_prototype.py            # 完整构建：Wine + Game + 启动器 + 签名
```

`build_prototype.py` 会用 `cp -cR`（APFS 克隆，同卷不额外占空间）把两份素材拷进 App，
再编译启动器、写 `Info.plist`、`codesign --force --sign -`（ad-hoc，不加 `--deep`）。

### 3.4 只改启动器的话（99% 的情况）

```sh
cd "/Volumes/SSD/Game/游戏构建/虐杀原形/_build"
python3 build_prototype.py --launcher      # 编译 + strip + 重签，几秒
codesign -v "/Volumes/SSD/Game/Prototype/Prototype.app" && echo 签名 OK
```

App 不在默认位置时：`PROTOTYPE_ROOT=/别的/路径 python3 build_prototype.py --launcher`。

### 3.5 首次运行

```sh
touch "$HOME/Library/Application Support/MacNativeGames/PROTOTYPE/autoplay"   # 可选：跳过面板
open -a "/Volumes/SSD/Game/Prototype/Prototype.app"
```

会依次发生：

1. 弹「想要访问"文稿"文件夹」→ **点允许**（存档在 `~/Documents/Prototype`，一次性）
2. 出现面板（第一次会写 `launcher-settings.json`）
3. 点「开始游戏」→ 首次会先 `wineboot -u` 建 prefix（约 1 分钟，没有进度条，别以为卡死）
4. 黑窗口 → 十几秒后出 `RADICAL ENTERTAINMENT` 片头（这一步实测能跑到 400 多帧）
5. 主菜单 → 载入存档

> 如果第 4 步卡在黑窗口不动：先看 `logs/launcher.log` 最后几行——
> 如果是「判定启动失败 + 重试」，说明命中了启动崩溃，看门狗会自己重来（打了 wow64cpu 补丁后
> 这一类实测 12 次 0 次）；如果日志里有「wow64cpu 补丁：未打」，先把它打上（第 10 节）。
> 如果既没重试也没出片头，多半是第 6 节第 19 条那个「从 Finder 启动」的问题，改用终端启动。

## 第 4 节 · 启动器面板

源码 `_build/launcher.m`（AppKit，无 nib）。**面板选项 → 落到哪里**：

| 面板项 | 落到 | 说明 |
|---|---|---|
| 渲染后端 | `WINEDLLOVERRIDES` | wined3d：`d3d9=b;winevulkan=d`；DXVK：`d3d9=n`。`Game/d3d9.dll` 不存在时这一项**直接灰掉**并强制 wined3d |
| 显示模式 | **Wine 注册表虚拟桌面**（窗口）或删掉该值（独占全屏） | 两种模式**启动命令完全一样**（`wine prototypef.exe`），只是注册表不同。窗口模式下启动器会用辅助功能 API 把窗口摆到屏幕正中 |
| 分辨率 | 只决定**虚拟桌面尺寸**（`HKCU\Software\Wine\Explorer\Desktops\Prototype`） | 不改变游戏内部渲染分辨率；**建议和游戏内 OPTIONS → VIDEO 的分辨率一致**，否则窗口里会出现黑边 |
| CPU 核心 | `WINE_CPU_TOPOLOGY=4:0,1,2,3` | **必须限 4 核**，不只是性能，是稳定性（见第 6 节第 4 条） |
| 帧率上限 | 写 `dxvk.conf` 的 `d3d9.maxFrameRate` | **wined3d 忽略它**；真正的锁帧靠游戏内 VSync |
| 日志 | `WINEDEBUG`（正常 `err+all`，详细 `,fixme+all`） | 不能用 `-all` |
| 提高进程优先级 | `taskpolicy -c user-interactive -p <wine pid>` | 减少被后台任务抢占的掉帧 |
| 把帧率写进日志 | `WINEDEBUG` 追加 `,fps` | 排查用，会明显掉帧，平时别开 |
| 备份存档 | 拷 `~/Documents/Prototype/*.bin` → `saves-backup/<时间戳>/` | 存 16 KB 一个，几乎不花钱 |

按钮：**开始游戏 / 结束游戏 / 存档目录 / 备份存档 / 日志 / 重置环境**。

**结束游戏**只管杀进程，不管界面状态——游戏卡死时窗口往往连关闭按钮都不响应，这是唯一可靠的收场方式。
**重置环境**会先杀会话再删 prefix（顺序反了会留下半截文件，下次 wineboot 更慢更容易失败）。

**跳过面板**（两种都行，第二种更可靠）：

```sh
open -a "/Volumes/SSD/Game/Prototype/Prototype.app" --args --play      # 实测 macOS 15 上有时不传参
touch "$HOME/Library/Application Support/MacNativeGames/PROTOTYPE/autoplay" && open -a "/Volumes/SSD/Game/Prototype/Prototype.app"
```

## 第 5 节 · 环境变量全表（启动器会自动设，手工排查时对照）

| 变量 | 值 | 作用 / 不加会怎样 |
|---|---|---|
| `WINEPREFIX` | `…/PROTOTYPE/prefix` | 必需 |
| `WINEDEBUG` | `err+all` | **不能用 `-all`**：会显著提高启动崩溃概率，而且崩溃信息被吞掉后看门狗没法判断 |
| `WINE_CPU_TOPOLOGY` | `4:0,1,2,3` | **必须设**，去掉会 `RtlpWaitForCriticalSection` 死锁后崩 |
| `WINEDLLOVERRIDES` | `d3d9=b;winevulkan=d` | 强制用内置 wined3d。**注意 `winevulkan=d` 挡不住 MoltenVK**：wined3d 的 Vulkan 能力探测是 unix 侧直接 dlopen `libMoltenVK.dylib`，绕过了 DLL 覆盖。真要关掉得把那个 dylib 改名（见第 6 节第 21 条） |
| `DXVK_CONFIG_FILE` | `…/PROTOTYPE/dxvk.conf` | 只在切 DXVK 时有意义；放数据目录是为了不污染 bundle 签名 |
| （不加 `LANG`） | — | 强行 `zh_CN.UTF-8` 会让 Wine 切代码页 936，实测几分钟后更容易死锁；路径保持英文是更省事的解法 |

外部还有一条（不在 env 里，启动器用 `taskpolicy` 调）：把 wine 进程提到 `user-interactive` QoS。

**绝对不要再加的三样**（都试过，只会更差）：

```
vulkan-1=d                    # 实测启动成功率 2/6，比不加还差
WINE_D3D_CONFIG=renderer=vulkan   # 能起来，一画就 0xc0000005 崩在 vkCreateBufferView
DXVK（d3d9=n + 一份 d3d9.dll）    # Metal 没有几何着色器，建不出 Vulkan 设备，必然失败
```

## 第 6 节 · 坑位清单（按严重程度排序，都踩过）

1. **App 路径不能有中文**。游戏用 ANSI 接口取自己的目录，中文会变 `????`，引擎初始化失败：
   白窗口 → 几十秒 → 静默退出。所以 App 叫 `Prototype.app` 而不是 `虐杀原形.app`。
2. **DXVK 这条路走不通，而且失败方式是"点了没反应"**。`d3d9=n` 的前提是 `Game/` 里有原生 `d3d9.dll`；
   没有的话 wine 找不到库，进程起不到一秒就退，**日志一个字都不留**。现在按文件存在与否自动灰掉这一项，
   启动前再拦一次，设置里存着 DXVK 也会自动切回 wined3d。
3. **配置文件不能写进 App 包里**。以前 `dxvk.conf` 写在 `Game/` 下，等于每次点开始游戏都在改 bundle 里的文件——
   codesign 的资源封印记的是内容哈希，内容一变 ad-hoc 签名就作废（`codesign -v` 报 resource modified）。
   现在写 `…/PROTOTYPE/dxvk.conf`，用 `DXVK_CONFIG_FILE` 指过去。
4. **`WINE_CPU_TOPOLOGY` 不能省**。不限制核心时 Wine 里会 `RtlpWaitForCriticalSection` 死锁，
   然后 `Exception frame is not in stack limits` 崩溃，一般跑一两分钟就挂。4 核是游戏自带 `Restrict Cores.bat`
   的值（`start /affinity F`）。
5. **`WINEDEBUG=-all` 是陷阱**。崩溃信息会被吞掉，看门狗没法判断，表现就是"卡在黑窗口里永远不动"。
   `err+all` 是安全下限。（早先还观察到 `-all` 会显著提高崩溃概率——现在看那只是同一个 Rosetta
   问题的巧合，不再作为结论。）
6. **强杀会留下占着 prefix 的服务进程**。`services.exe` / `winedevice.exe` / `plugplay.exe` 的命令行里只有
   `C:\windows\system32\...`，没有 App 路径，所以 `pkill -f "Resources/Wine"` 抓不到它们。
   正确做法是按**可执行文件路径**枚举（启动器里的 `CollectWinePids` 就是这么干的，用的是 `proc_pidpath`）。
7. **`open --args` 不保证把参数送进进程**。macOS 15 上实测：面板出来了，但 `arguments` 里没有 `--play`，
   于是永远不开始。所以加了 `autoplay` 标记文件这条路，任何启动方式都成立。
8. **启动崩溃的真正根因：Rosetta 2 的 32/64 位模式切换（已根治）**。
   崩溃长这样，而且**跟游戏本体、显卡、分辨率、模组全都无关**：
   ```
   wine: Unhandled page fault on read access to 00002DC1 at address 7BF21239 (thread 010c), starting debugger...
   err:virtual:virtual_setup_exception nested exception on signal stack addr 0x7ff80d259ef4 stack 0x7ff001caf980
   err:seh:NtRaiseException Exception frame is not in stack limits => unable to dispatch exception
   ```
   用 `WINEDEBUG=+module` 抓模块表可以看出来：`0x7BF20000` 是 `wow64cpu.dll` 的装载基址，
   偏移 `0x1239` 和 `0x1135` 正好是 syscall / unixcall 的 **32→64 位入口 thunk**。反汇编这两处：
   ```
   +0x1239:  8b 15 c1 2d 00 00   mov edx,[rip+0x2dc1]     ← 读 0x2DC1
   +0x1135:  8b 15 c5 2e 00 00   mov edx,[rip+0x2ec5]     ← 读 0x2EC5
   ```
   虐杀原形是 PE32，在 Apple Silicon 上只能走 Wine 的新式 WoW64（64 位进程里装 32 位 PE），
   每次系统调用都要在两种 CPU 模式间切换。Rosetta 2 偶尔**不真正切换**，于是 CPU 还在 32 位模式下
   执行 64 位的跳转指令，把指令里的位移字段当成内存地址去读 —— 那个低地址当然不存在，必然 page fault。
   这一条解释了全部怪现象：为什么是**概率性**的、为什么重试有时能成、为什么 64 位的霍格沃茨完全没事。

   **修法**：给 `wow64cpu.dll` 打二进制补丁（`_build/wow64cpu_rosetta_patch.py`，
   逻辑取自 GitHub 上 [altium-wine](https://github.com/lazy-jubei/altium-wine) 的同名补丁）——
   两个 32→64 入口改走"能判断当前 CPU 模式"的 trampoline（`push 0x2b; push ecx; retf` 重试切换），
   两个 64→32 返回站点改成在栈上构造 `iretq` 帧后用 `iretq` 返回。补丁先校验四个站点的原始字节，
   对不上就拒绝执行；原文件备份为同目录 `wow64cpu.dll.orig`。改完必须重新签名：
   ```
   codesign --force --deep -s - /Volumes/SSD/Game/Prototype/Prototype.app
   ```
   实测 **12 次启动 0 次崩溃**（打补丁前 11 次样本 6 次成功）。
   Note：Wine 官方把这类问题判成 NOTOURBUG（Rosetta 侧的问题），所以换 Wine 版本补丁会消失、
   也不会被官方修掉——`launcher.log` 里每次启动都写一行 `wow64cpu 补丁：已打 / 未打`，就是判据。

9. **看门狗仍然要留**。补丁之后还剩下两种少见失败，都靠它兜：
   ```
   日志停在同一行，没有任何崩溃特征，卡在 800×450 黑窗口里（静默卡死）
   ```
   这种情况用 CPU 判据——**20 秒内整个会话吃掉不到 0.2 CPU 秒 = 没在干活**。
   阈值是标定出来的，不是拍的（`proc_pid_rusage` 实测，`launcher.log` 里每次都会写一行 `CPU 判据`）：

   | 状态 | 20 秒窗口累计 CPU |
   |---|---|
   | 健康启动（正在解包/编译着色器/出帧） | **0.50 ~ 0.74 秒** |
   | 静默卡死（主线程等一个不来的事件） | **0.03 ~ 0.11 秒** |

   不要用"多少秒没画面"——游戏跑起来之后日志本来就不再输出，这条规则会把正在玩的一局误杀。
10. **看门狗和进程退出回调会重复记账**。崩溃退出时两条路径都会走到"重试"，各 `attempt++` 一次，
    5 次预算变成了 2 次半（实测：第 3 次失败后日志直接跳到「第 5 次」）。用 `watchdogFired` 标记
    让退出回调在看门狗已经判死的情况下直接返回。
11. **`wineserver -k` 不能等它的回调**。崩溃现场常挂着 `winedbg`，`-k` 有时卡住不返回，回调不触发就永远不重试。
    必须自己轮询"进程真的没了"再重启，而且**不能立刻重启**（`-k` 是异步的，1.5 秒后重开会撞上没退干净的旧会话）。
12. **看门狗日志定位要用分隔行，不能用文件偏移**。日志里每次启动写一行
    `===== 第 N 次启动 <时间> =====`，按偏移量算一旦错位就会去扫上一次的崩溃信息然后误判。
13. **wined3d 把显卡厂商认成 NVIDIA**。日志里 `Received unrecognized GL_VENDOR "Apple". Returning HW_VENDOR_NVIDIA.`
    是 fixme 级噪音，不影响运行；注册表里改 `DriverDesc` 也没用，它看的是 GL 返回的厂商串。
14. **`GL_ARB_uniform_buffer_object` 之类的 GLSL 扩展警告是噪音**。日志里几百条，
    是 Apple 的 GLSL 编译器在 core profile 下的输出，不影响画面也不影响帧率。
15. **虚拟桌面尺寸 ≠ 游戏内渲染分辨率**。面板的分辨率只决定那个窗口多大，游戏自己画多少在 OPTIONS 里改。
16. **锁帧只有一条路**：游戏内 `OPTIONS → VIDEO → Vertical Sync = ON`（写进 `profile.bin`，设一次就够）。
    wined3d 忽略 `dxvk.conf` 的 `maxFrameRate`。VSync 关掉时片头能跑到 490 fps，对无风扇的 Air 是白烧电。
17. **补丁后仍有一种独立失败**：`err:d3d:wined3d_swapchain_resize_buffers Something's still holding back buffer 0`
    （交换链 resize 时挂掉，12 次里出现 1 次）。跟 wow64 那条无关，看门狗重试一次就过去了；
    如果它变频繁，先把面板改成「窗口模式」而不是虚拟桌面。
18. **别同时开两个启动器**。没有单实例保护，两个会话会抢同一个 prefix，两个都别想正常跑。
19. **`open -a`（等于双击）和目录里直接跑 App 二进制，行为不一定一样**。实测到的确定差别只有一条：
    用 `open -a` 时，虚拟桌面模式下的 explorer 会起来、但**游戏进程永远不出现**
    （日志只有 171 行 explorer 初始化，21 秒烧 0.03 CPU 秒）；同一个命令从 shell 起就正常拉起游戏。
    已排除：`LANG` 缺失、`TMPDIR`、`stdin`、自动启动延迟、`taskpolicy` 高优先级，
    以及用 `env -i` 复刻 LaunchServices 的最小环境（复刻不出来）——所以不是环境变量，是会话上下文。
    兜底已加：虚拟桌面 8 秒内见不到游戏进程就自动改直连（写进 `launcher.log`），并把选择记进设置
    `forcedirect`；「重置环境」会清掉它。
    **注意**：黑屏 0 fps 那种现象后来又出现在所有路径上（包括本来正常的 shell 路径），
    所以它和上面这条不是同一个问题，见第 20 条。
20. **黑屏 0 fps**：窗口出来了、一直是黑的、日志里 `@ approx 0.00fps` 并且行数不再增长。
    游戏进程活着、CPU 也不是 0，所以**看门狗的 CPU 判据抓不到**，会一直挂着。
    实测是在反复切换「虚拟桌面 / 独占全屏」之后出现的，怀疑游戏把显示模式写进了
    `~/Documents/Prototype/profile.bin`，之后每个会话都按那个模式建不出可用的交换链。
    恢复顺序（从轻到重）：
    1. 能进画面的话，游戏内 `OPTIONS → VIDEO` 把分辨率/全屏改回 1280×720 + 窗口
    2. 进不去就**备份后**删 `profile.bin`（它是画面设置 + 进度索引；存档在 `slot-*.bin`，不受影响）：
       ```sh
       mkdir -p ~/Documents/Prototype.bak
       cp ~/Documents/Prototype/profile.bin ~/Documents/Prototype.bak/
       rm  ~/Documents/Prototype/profile.bin
       ```
    3. 还不行就重启一次 Mac（清 WindowServer/GPU 状态），或点面板「重置环境」
    判据：正常启动第一帧就是几百 fps（`@ approx 490.34fps`），`0.00fps` 就是坏状态。
21. **启动崩溃的最后一块：MoltenVK（2026-10-30 定位并根治）**。
    症状：启动 3 秒左右直接退出，`launcher.log` 写「启动后 3.2 秒就退出（代码 5）」或
    「启动静默卡死」，`prototype.log` 里唯一的相关行是
    ```
    00f8:err:seh:send_debug_event Exception c0000005 in system thread at 0x7ff81136a622
    ```
    它不是 wow64cpu 那条（地址不在 `0x7BF2xxxx`），所以打完 wow64 补丁仍然会发生。
    真凶是 **wined3d 初始化时会无条件建一个 Vulkan 实例做能力探测**——日志里那一大段
    `[mvk-info] MoltenVK version 1.4.0 ... Created VkInstance` 就是它。这个初始化在 Rosetta 下
    会概率性把进程带崩。`WINEDLLOVERRIDES` 里的 `winevulkan=d` **管不住它**（探测走 unix 侧
    直接 dlopen），所以之前一直以为「已经关了 Vulkan」其实没关。

    **修法**：把 `Contents/Resources/Wine/lib/libMoltenVK.dylib` 改名成 `.disabled`
    （构建脚本 `step_tweaks()` 会自动做，改完必须重新签名）。D3D9 走 OpenGL，用不到 Vulkan，无副作用。
    实测：开着 4 次启动挂 1~2 次；禁掉之后**连续 4 次全成功**（片头 386~498 fps），
    走启动器（双击）路径又连测 3 次，全部第 1 次就起来。
    `launcher.log` 每次启动都会写一行 `MoltenVK：已禁用 / 未禁用`，就是判据。
22. **窗口化不要再用 `wine explorer /desktop=...`**。从 LaunchServices（双击 / `open -a`）启动时，
    explorer 能起来但游戏进程永远不出现——日志只剩一百多行 explorer 初始化，20 秒烧 0.03 CPU 秒。
    同一份命令从终端跑就正常，复刻环境变量也复刻不出来（是会话上下文差异）。
    现在改成**写 Wine 注册表**：
    ```
    HKCU\Software\Wine\Explorer            Desktop = Prototype
    HKCU\Software\Wine\Explorer\Desktops   Prototype = 1024x768
    ```
    启动命令退化成最可靠的 `wine prototypef.exe`，由 wine 自己建虚拟桌面窗口。
    全屏模式 = 删掉 `Desktop` 这个值。实测双击路径也正常。
23. **窗口居中要用辅助功能 API，而且只对虚拟桌面窗口安全**。
    Wine 的虚拟桌面窗口默认贴在屏幕左上角（`0,25`），要用 `AXUIElementSetAttributeValue(kAXPositionAttribute)`
    摆到正中（`1024x768` 在 1920×1080 上就是 `448,156`）。启动器 `startCentering` 干这件事。
    - 需要给**启动器**授权「辅助功能」。签名要求已经固定成 `identifier`
      （`build_prototype.py` 里的 `--requirements`），所以重建启动器**不会**让授权失效。
    - 授权之后必须退出启动器（Cmd+Q）重开一次——运行中的实例会缓存旧的 TCC 判定。
    - **不要对「直连」窗口做同样的事**：直连模式下那个窗口是游戏自己的交换链窗口，
      用 AX 挪它会让画面错位，接着游戏直接退出（代码 0）。

## 第 9 节 · 性能基线与调优边界

**实测数据（1280×720 虚拟桌面，4 核，VSync 关，2026-10-28）**：

| 阶段 | FPS | 备注 |
|---|---|---|
| 片头 logo / 加载 | **330 ~ 490** | `wglSwapBuffers` 节拍实测，这一阶段的帧率上限就是驱动能吃下的量 |
| 主菜单（城市背景） | **8 ~ 19** | 上一版实测；同一套环境、同一个进程 |
| 单次启动成功率 | **12/12（补丁后）**；补丁前约 50%（11 次样本 6 次成功） | 判据是 45 秒窗口内是否出现 `page fault`，见 `_build/soak3.sh` |

启动崩溃的分布（补丁前 `launcher.log` 累计）：page fault（`wow64cpu` 模式切换，见第 6 节第 8 条）
和静默卡死大约各占一半。**打完 wow64cpu 补丁后 page fault 这一类不再出现**，
12 次里只剩 1 次交换链 resize 失败（第 6 节第 17 条）。

**瓶颈判断（决定哪些优化有用）**：

- 同一套配置，片头 490 fps、主菜单 10 帧 → **不是分辨率、不是填充率、不是显存**。
  差别在这一幕的绘制量：wined3d 要把每条 D3D9 调用翻译成 OpenGL，而 Apple 的 OpenGL 驱动早就停止维护；
  再叠上 Rosetta 2 翻译 32 位 x86 指令。**瓶颈在 CPU 侧的翻译链。**
- 所以「降分辨率 / 降画质」对主菜单收益有限——它减的是 GPU 的活，而 GPU 不是瓶颈。
- 真正能减的只有"少画东西"：关阴影、降细节（减少 draw call 数量），这在游戏内 OPTIONS 里。
  这一项没在本机做过逐档对比，别把它当成定论。

**还能做的**：

1. 关掉其它吃内存/CPU 的 App（这台是 16 GB，效果最直接）。
2. 主菜单卡就卡着——它只是菜单。进游戏场景之后再看帧率，才是真实体验。
3. 游戏内 `OPTIONS → VIDEO`：降分辨率、关阴影、关 AA。能跑满的场景把 VSync 打开省电。

**别做（都试过，白费时间）**：

| 想法 | 结论 |
|---|---|
| 换 DXVK | Metal 没有几何着色器（`VkPhysicalDeviceFeatures` 第 5 个字段），MoltenVK 报不出来，D3D9 的 DXVK 实现必然建不出设备。换 MoltenVK 版本没用 |
| wined3d 的 Vulkan 渲染器 | 能起来，一画就崩 `0xc0000005 in vkCreateBufferView` |
| 用 D3DMetal（霍格沃茨那套 GPTK 3.0-3） | GPTK 的 `wine/i386-windows/` 里**只有 `ddraw.dll`，没有 `d3d9.dll`**——D3DMetal 不做 D3D9。这条路对本游戏不存在 |
| vkd3d-proton | 需要 `VK_EXT_transform_feedback`（Metal 没有 stream output），而且它是 D3D12 的，跟 D3D9 无关 |
| 关日志（`-all`）提速 | 会显著提高启动崩溃概率，还吞掉看门狗的依据。得不偿失 |
| 加 `vulkan-1=d` 降崩溃 | 实测 2/6，比不加更差，已排除 |
